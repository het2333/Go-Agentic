## 开场案例：Agent 如何知道自己真的修好了？

用户只给出一句目标：“运行 `check_hello.py`，分析失败原因，只修改 `hello.py`，最后重新验证。”初始实现直接返回用户名，测试要求删除首尾空白。一个单文件 Coding Agent 得到的不是答案材料，而是工作目录和四个受控工具；接下来的轨迹由新证据推动：

| 轮次 | 模型选择 | Harness 实际执行 | 新证据 |
| --- | --- | --- | --- |
| 1 | 运行检查 | `python3 check_hello.py` | 退出码非零，断言失败 |
| 2 | 读取相关文件 | `read_file("hello.py")` | 定位到 `return username` |
| 3 | 写入最小修复 | 改为 `return username.strip()` | 文件已经更新，但尚未证明正确 |
| 4 | 再次运行检查 | `python3 check_hello.py` | 退出码为零，四个用例通过 |
| 5 | 返回最终说明 | 停止循环 | 回答引用了刚获得的验证结果 |

### 先校正一句流行说法

你可能见过一句很有冲击力的二次改写：

> “如果你不能在 300 行内写出一个智能体，你最多只能算初级工程师。”

它适合当作学习挑战，却不适合当作工程师等级标准，也没有可靠证据表明这是某位作者的原话。代码短不等于系统安全，代码长也不等于理解深入。真正可以核验的是 Geoffrey Huntley 在 *How to Build a Coding Agent* 中的表述：

> “It’s not that hard to build a coding agent. 300 lines of code running in a loop with LLM tokens.”

更准确的中文理解是：**最小 Coding Agent 并不神秘，它可以由大约 300 行普通代码、一个 LLM 和一个持续获得反馈的循环组成。** 本节把“300 行”当作拆除神秘感的练习：你不必记住每行语法，但应该能说清每个模块为什么存在、数据从哪里来、动作由谁执行、什么证据允许结束。

- [阅读 Geoffrey Huntley 的原文](https://ghuntley.com/agent/)
- [打开 266 行教学版 `coding_agent_beginner.py`](https://github.com/het2333/Go-Agentic/blob/main/code/go-agentic/01-minimal-loop/coding_agent_beginner.py)
- [对照 444 行安全增强版 `coding_agent.py`](https://github.com/het2333/Go-Agentic/blob/main/code/go-agentic/01-minimal-loop/coding_agent.py)

### 为什么同时保留 266 行版和 444 行版

266 行版负责把机制讲明白；444 行版负责展示机制进入真实环境后会遇到的安全细节。不要为了凑“300 行”把防护压缩成难读的一行，也不要让安全代码挡住第一次理解循环。

| 版本 | 适合做什么 | 刻意保留或省略什么 |
| --- | --- | --- |
| 266 行教学版 | 在临时目录跑通一次完整闭环，逐块阅读 | 保留四个工具、模型接口、消息历史和轮数上限；路径保护是教学级实现 |
| 444 行安全增强版 | 学习更严格的文件描述符边界、响应校验、超时和进程清理 | 代码更长，但能解释符号链接竞争、重定向、异常响应和环境变量泄露等真实风险 |

**第一次运行只使用临时练习目录。** 教学版的 `--workspace` 不是操作系统沙箱；启用 `--allow-run` 后，子进程仍拥有当前用户权限。理解循环后，再阅读安全增强版。

### 把 266 行代码看成六个积木

| 积木 | 代码入口 | 直观类比 | 它解决的问题 |
| --- | --- | --- | --- |
| 工作规则 | `SYSTEM` | 写给临时同事的任务说明 | 告诉模型先检查、再修改、最后验证 |
| 能力菜单 | `TOOLS`、`function_tool()` | 菜单只描述能点什么 | 让模型产生结构化 Tool Call，而不是含糊地说“我想读文件” |
| 工作台 | `Workspace` | 真正拿起工具的双手 | 读取、写入、运行命令，并把结果返回 |
| 模型连接器 | `ChatModel` | 把本地消息送到模型的快递员 | 组装 HTTP 请求并取回 assistant 消息 |
| Agent 心脏 | `run_agent()` | 一直转动的反馈轮 | 保存决定、执行工具、追加 Observation、进入下一轮 |
| 启动按钮 | `main()` | 开机与接线 | 读取参数和环境变量，组装模型、工作台与循环 |

图中 `run_command("python app.py")` 是流程示意；本章代码实际接收参数数组：`run_command(["python3", "app.py"])`，不会把整段字符串交给 Shell。

#### 积木一：`SYSTEM` 和 `messages` 是工作记忆

程序启动时先放入两条消息：

```python
messages = [
    {"role": "system", "content": SYSTEM},
    {"role": "user", "content": task},
]
```

可以把 `messages` 想成桌上的任务记录本。`system` 写长期规则，`user` 写本次目标。此后模型的决定用 `assistant` 保存，工具结果用 `tool` 保存。模型每轮重新看到这本记录本，才知道刚才做过什么。它不是长期记忆：程序退出后，这个列表就消失。

#### 积木二：`TOOLS` 是菜单，不是执行器

下面的 Schema 只告诉模型工具叫什么、需要哪些参数：

```python
function_tool(
    "read_file",
    "读取一个 UTF-8 文本文件。",
    {"path": PATH},
    ["path"],
)
```

它不会读取任何文件。就像菜单上的“番茄炒蛋”不会自己做饭，模型输出 `read_file({"path": "hello.py"})` 也不会改变电脑。真正的副作用只发生在 `Workspace.execute()` 找到对应 Python 函数以后。

#### 积木三：`Workspace` 是 Agent 的手

`Workspace` 提供四个动作：列目录、读文件、写文件、运行程序。`safe_path()` 先把模型给出的相对路径放到工作目录下，再拒绝逃到目录外的路径。`run_command()` 接收参数数组而不是一整段 Shell 字符串，因此 `&&`、重定向和通配符不会被 Shell 自动解释。

```python
result = subprocess.run(
    argv,
    cwd=self.root,
    capture_output=True,
    text=True,
    timeout=self.command_timeout,
    shell=False,
)
```

这里最重要的返回值不是漂亮文字，而是 `exit_code`。`0` 通常表示程序成功结束，非零表示失败。测试失败也是有价值的 Observation，因为它告诉模型下一步应该调查哪里。

#### 积木四：`ChatModel` 只是模型接口

`ChatModel` 把 `model`、`messages` 和 `tools` 编码为 JSON，通过 HTTP 发给模型服务，再取出 `choices[0].message`。模型可能返回普通文字，也可能返回 `tool_calls`。这层不负责改文件，因此更换模型服务时，`Workspace` 和主循环不必一起重写。

API Key 只进入请求头，不应该写进教程代码或提交到 Git。教学版接受兼容 Chat Completions Function Calling 的服务；不同 API 协议需要改写这一层，而不是改写整个 Agent。

#### 积木五：`run_agent()` 是真正的 Agent Loop

去掉打印和防御检查后，核心只有下面几步：

```python
for round_number in range(1, max_rounds + 1):
    message = model(messages, tools)       # 模型选择下一步
    messages.append(message)               # 保存这次决定
    calls = message.get("tool_calls") or []

    if not calls:
        return message["content"], messages

    for tool_call in calls:
        observation = workspace.execute(tool_call)
        messages.append({
            "role": "tool",
            "tool_call_id": tool_call["id"],
            "content": observation,
        })
```

逐行翻译成人话就是：

1. 把目前知道的一切交给模型；
2. 模型选择回答，或者请求一个工具；
3. Python 执行工具，模型本身不执行；
4. 把真实结果记回 `messages`；
5. 带着新证据再问模型；
6. 模型不再请求工具时结束，或在轮数耗尽时强制停止。

`tool_call_id` 像快递单号。模型一轮可能申请多个工具，返回结果必须带原来的 ID，服务才能知道哪个结果对应哪个请求。

#### 积木六：`main()` 负责把零件接起来

`main()` 读取任务、工作目录、轮数和 `--allow-run`，再从环境变量取得模型配置。它先创建 `Workspace`，再创建 `ChatModel`，最后调用 `run_agent()`。这部分是启动代码，不是推理逻辑。

### 跟着 `hello.py` 走完一圈

| 时刻 | `messages` 新增什么 | 环境真的发生了什么 | Agent 现在知道什么 |
| --- | --- | --- | --- |
| 开始 | system 规则 + user 任务 | 什么都没发生 | 只知道目标，不知道代码是否有错 |
| 第一次检查 | assistant 请求 `run_command`；tool 返回 `exit_code=1` | Python 执行检查脚本 | 缺陷被真实复现 |
| 读取代码 | assistant 请求 `read_file`；tool 返回文件内容 | 文件只被读取 | 看见 `return username` |
| 写入修复 | assistant 请求 `write_file`；tool 返回“已写入” | `hello.py` 变成 `.strip()` | 只证明改过，尚未证明正确 |
| 再次检查 | assistant 再请求 `run_command`；tool 返回 `exit_code=0` | 检查脚本重新运行 | 获得新的通过证据 |
| 结束 | assistant 返回普通文字 | 不再执行工具 | 可以说明修改和验证结果 |

注意第三步和第四步之间的区别：**“已写入文件”不是“已经修好”。** 写入回执只证明 Action 发生了；重新运行检查得到的零退出码才是本任务的 Verification。

### 最容易误解的五件事

1. **Prompt 不是 Agent。** 它只给规则；循环、工具与环境共同组成可行动系统。
2. **Tool Call 不是副作用。** 模型只是提交结构化请求，Python 才真正执行。
3. **最终回答不是成功证据。** 模型说“已修复”不能替代测试输出。
4. **工作目录不是沙箱。** 特别是命令工具仍拥有当前用户权限，所以先用临时目录。
5. **300 行只是入口。** 生产系统还需要精确编辑、审批、持久状态、上下文压缩、回滚、审计和独立评测；这些将在后续章节逐步加入。

这个案例先展示了聊天模型和 Agent 的分界：聊天模型生成回答；Agent 在环境中推进任务。两者常使用同一类大语言模型，但 Agent 还需要工具、状态、控制循环、权限边界和可验证的停止条件。本章建立全书统一术语，并用一个无需 API Key、无需网络的登录故障案例拆解最小 Agent Loop。

## 1.1 Agent 的边界

### 1.1.1 六个必须分开的概念

本课程所说的 **Agent**，是一个面向目标的系统：它根据当前状态选择行动，通过工具影响环境，读取行动结果，并在满足成功或停止条件前重复这一过程。LLM 可以充当决策部件，但单独一次模型调用还不是 Agent。

| 概念 | 职责 | 不负责什么 |
| --- | --- | --- |
| Model | 根据输入消息生成文本或结构化决策 | 不会自行读取文件或执行命令 |
| Agent | 围绕目标选择下一步，并根据观察调整 | 不等于承载它的完整软件系统 |
| Framework | 提供构建 Agent 的代码抽象 | 不替具体任务定义成功标准 |
| Harness | 组装模型、工具、上下文、循环和安全控制 | 不替模型决定每一步内容 |
| Runtime | 让 Harness 持续运行，管理会话、进程和资源 | 不等于任务所处的外部世界 |
| Environment | 文件、终端、浏览器、API 或业务系统等可观察、可改变的对象 | 不负责推理 |

**工具（Tool）** 是 Agent 穿过系统边界的受控接口。读取文件、查询数据库和运行测试都是工具调用；模型输出的“我已经修复”只是一段文本，直到环境真的发生变化并返回证据。

### 1.1.2 四类边界

一个可控任务至少要写清四类边界：

1. **任务边界**：目标是什么，哪些结果不在本次任务内；
2. **环境边界**：Agent 能观察哪些系统，哪些状态是未知的；
3. **权限边界**：哪些工具可用，哪些行动需要人工批准；
4. **终止边界**：什么证据代表成功，何时因步数、成本、时间或错误停止。

例如“检查项目为什么登录失败，修复问题并运行相关测试”已经给出目标，但仍需补充允许修改的目录、相关测试命令、最大尝试次数和成功证据。自主性来自边界内的选择空间，而不是无限权限。

## 1.2 最小 Agent Loop

### 1.2.1 Environment 与 Observation

Agent 一开始看不到完整环境。它只能通过工具获得局部信息：命令退出码、测试输出、文件片段、搜索结果或 API 响应。Harness 把这些结果封装成 **Observation**，加入下一轮决策上下文。

观察必须忠实保留能改变决策的事实。例如测试失败时，测试名、错误类型、相关路径和退出状态通常比整段日志更重要。截断、总结或格式化都不能把“失败”改写成“成功”。

### 1.2.2 Action、Verification 与 Termination

**Action** 是一个带名称和参数的结构化工具请求。Harness 校验它、执行对应工具，并把结果变成新的观察。**Verification** 是用独立证据检查目标是否实现；“文件已编辑”证明行动发生了，只有相关测试通过才能证明这个案例的目标成立。


一个最小循环可以写成：

```python
observations = []
for step in range(1, max_steps + 1):
    decision = policy.decide(task, tuple(observations))
    if isinstance(decision, FinalAnswer):
        return finish_only_if_verified(decision, observations)
    observations.append(dispatch_and_observe(decision))
return stop_at_step_limit(observations)
```

这段循环有三个关键性质：

- 每次只执行一个可记录的行动；
- 工具错误也会成为观察，而不是让控制流悄悄消失；
- 达到最大步数时必然停止，最终答案不能替代验证证据。

## 1.3 Workflow 与自主 Loop

### 1.3.1 在不确定性出现的位置划分控制权

先从终点证据倒推。对于“发布一个补丁版本”，成功意味着候选版本通过全部必需检查、批准已经记录、预期 Artifact 已发布，而且发布后的健康检查通过。这组条件会暴露哪些决定能够预先固定，哪些决定需要现场解释。

| 循环阶段 | 固定 Workflow 的职责 | 自主 Loop 的职责 |
| --- | --- | --- |
| Observe | 收集指定 CI 检查、Artifact Digest、批准状态与部署健康状态 | 只用获准的日志、文件和测试调查意外失败 |
| Decide | 按预设分支处理通过、失败、批准、发布与回滚 | 根据最新证据选择下一次诊断探查 |
| Act | 执行已批准的构建、发布或回滚操作 | 在工作区内读取、搜索、测试或准备有界修复 |
| Verify | 将检查记录和部署状态与发布契约比较 | 向 Workflow 提供证据，不能跳过发布门槛 |

假设 Artifact 校验和通过，但 Smoke Test 在一个陌生路由上失败。Workflow 在发布前停止，把失败 Observation 交给 Agent。Agent 决定检查失败请求，读取有界日志，并观察到一个过期的环境变量键引用。它修正引用并重新运行 Smoke Test。只有新 Observation 显示通过后，Workflow 才会请求批准、发布 Artifact，并验证服务健康。Agent 负责消除不确定性，Workflow 继续掌握发布权限。

### 1.3.2 测试决策，不测试某个模型的措辞

Harness 测试中的自主部分仍然可以是确定性的。Fake Policy 可以把 `smoke_failed` 映射到 `read_log`，把 `stale_key_found` 映射到 `read_file`，把 `repair_ready` 映射到编辑，再把 `candidate_updated` 映射到 `run_smoke`。Fixture 控制每次返回的 Observation，其中包括 Tool Error 和 Verification 失败。断言由此覆盖所选 Action、进入下一次决策的证据、批准边界和步数预算。

真实模型可能采用不同措辞，也可能选择另一个获准的探查动作。系统契约仍然可测试，因为权限、Observation、Verification 与 Termination 都属于 Harness。

## 1.4 五分钟实践：诊断登录失败

### 1.4.1 运行离线 Fixture

本章代码位于 `code/go-agentic/01-minimal-loop/`。它只依赖 Python 标准库；测试使用 pytest，不访问网络，也不读取环境变量。

```bash
python3 -m pytest code/go-agentic/01-minimal-loop/test_agent.py -q
```

Fixture 模拟一个用户名没有去除首尾空格的登录缺陷。它不是 Pi API 的复刻，而是一个 **Pi 风格** 的教学 Harness：模型策略只决定下一步，Harness 掌握工具执行、观察记录、错误处理、验证和终止。Pi 是本课程唯一连续实践主线；第 7 章再进入真实 Pi Runtime。

### 1.4.2 类型化工具协议

策略不能直接修改环境，只能产生两类决策：

```python
ToolCall(
    name="read_file",
    arguments={"path": "src/auth/login.py"},
)

FinalAnswer("Login normalization fixed; the focused test passes.")
```

三个工具的契约如下：

| Tool | 必需参数 | 成功观察 | 可能错误 |
| --- | --- | --- | --- |
| `run_tests` | `target` | `PASS ...` 或 `FAIL ...`；只有 PASS 标记为 verified | 未知测试目标 |
| `read_file` | `path` | 文件内容 | `FileNotFoundError` |
| `replace_text` | `path`, `old`, `new` | `UPDATED ...` | 文件不存在或旧文本不匹配 |

工具抛出的异常会被转换为 `TOOL_ERROR <类型>: <消息>`。这让策略能在下一轮恢复，也让测试和审计日志看到失败。

### 1.4.3 从失败到证据的轨迹

确定性策略产生以下轨迹：

| Step | Action | Observation | 含义 |
| --- | --- | --- | --- |
| 1 | `run_tests(tests/test_login.py)` | FAIL，指向 `src/auth/login.py` | 先读取真实失败 |
| 2 | `read_file(src/auth/login.py)` | 返回缺陷实现 | 检查相关文件 |
| 3 | `replace_text(...strip())` | UPDATED | 采取最小行动 |
| 4 | `run_tests(tests/test_login.py)` | PASS，`verified=True` | 用环境证据验证 |
| 5 | `FinalAnswer(...)` | 停止 | 仅在上一观察已验证时完成 |

测试还覆盖两条失败路径：缺失文件会成为可恢复观察；永不结束的策略会在 `max_steps` 后以 `max_steps` 状态停止。由此，Fixture 的精确顺序“运行聚焦测试 → 读取相关文件 → 替换缺陷文本 → 再次运行聚焦测试 → 根据已验证结果停止”不再只是叙述，而成为可执行、可断言的 Agent Loop。

## 1.5 设计一个最小 Agent 的检查表

在加入记忆、多智能体或复杂规划前，先回答：

- 目标、允许范围和成功证据是否明确？
- 每个工具是否有名称、参数 Schema、返回值和错误语义？
- Observation 是否包含下一步真正需要的环境事实？
- 验证是否独立于模型自述？
- 是否有最大步数、时间、成本和人工批准边界？
- 是否能保存完整轨迹并重放关键失败？

如果这些问题没有答案，增加更多模型推理通常只会放大不确定性。

## 1.6 本章小结

- Model 负责生成决策；Agent 在 Harness 控制下用工具与 Environment 交互；Runtime 承载持续执行。
- 最小语义是 Observation—Action—Verification：观察环境，采取结构化行动，用新证据验证。
- Workflow 预先确定路径，自主 Loop 在运行时选路；生产系统常组合二者。
- 工具错误必须可观察，成功必须有证据，循环必须有终止预算。
- 离线登录 Fixture 用确定性策略证明了从失败、检查、修改到验证的完整闭环。

## 掌握标准

当你能在不使用“它会自己想办法”这类模糊表述的情况下，画出一个 Agent 的边界和循环；能指出每个行动的执行者、每个观察的来源、成功证据和停止条件；并能独立运行、解释四个 Fixture 测试时，即达到本章要求。

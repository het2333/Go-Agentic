深度研究不是“搜索很多页面，再写一篇长答案”，而是受控的证据生命周期。Agent 先定义可回答问题，再拆解问题、从不同角度检索、筛选来源、提取边界明确的证据、把主张与证据相连、保留矛盾，只综合有支持的陈述，为其添加引用、表达置信度，并因明确理由停止。

本章始终使用一个固定问题：**Meridian 的 2025 年电动公交试点是否降低了工作日能耗？结论有哪些限制？** 本地文档和 `.example` URL 都是虚构 Fixture，用于让证据行为可重复、可测试。

学完本章后，你应该能够：

- 把开放请求转换为范围明确的研究契约和检索计划；
- 实现查询多样化与来源排序，不把重复来源误认为独立佐证；
- 建立包含引文、定位、立场和溯源信息的主张—证据账本；
- 拒绝无支持主张，并完整保留矛盾双方；
- 产出主张级引用、经校准的置信度、可见 UI 状态和可辩护的停止决定。

## 14.1 研究契约与证据生命周期

### 14.1.1 先定范围，再搜索

有效的研究契约要固定对象、时间、比较项、结果、排除项和输出。本例契约如下：

| 字段 | 契约 |
| --- | --- |
| 对象 | Meridian 的 2025 年电动公交试点 |
| 比较 | 有记录的工作日基线与试点期工作日能耗 |
| 结果 | 能耗变化方向及报告幅度 |
| 必需限制 | 样本与测量限制 |
| 排除项 | 维护成本与无证据的全市外推 |
| 产物 | 简洁答案、主张账本、不确定性、引用、停止理由 |

如果“工作日”“基线”或“试点”含义不清，Agent 进入 `needs_scope` 并请求人工介入。目标未定义时，增加搜索量也无法修复问题。

### 14.1.2 生命周期就是控制 Loop

```text
定范围 → 拆解 → 查询多样化 → 筛选来源 → 提取证据
  ↑                                      ↓
停止/继续 ← 验证引用 ← 综合 ← 评估主张与矛盾
```

每条箭头都产生可复核状态。搜索结果只是候选项，不是证据；来源经过筛选、去重后才可使用；段落与具体主张相连后才成为证据；草稿通过主张和引用验证后才成为最终产物。

## 14.2 问题拆解与查询多样化

### 14.2.1 按证据需求拆解

Fixture 计划包含四个子问题：

1. **基线：** 有记录的工作日基线是多少？
2. **结果：** 试点测得了什么？
3. **测量：** 报告数值是否经过独立检查或修正？
4. **限制：** 哪些样本和设计限制约束了推断？

这些是证据需求，而不是报告标题。每个子问题都有完成条件。“测量”必须执行修正或矛盾检索才算完成；“限制”若只找到宣传性主张，也不算完成。

### 14.2.2 让意图、词汇和来源目标多样化

用同一句话重复搜索八次不叫多样化。应改变三个维度：

| 维度 | 示例 | 目的 |
| --- | --- | --- |
| 意图 | 基线、结果、审计、限制 | 覆盖不同证据需求 |
| 词汇 | `energy`、`kWh`、`meter`、`calibration` | 避免锁死在一种术语上 |
| 来源目标 | 交通部门、审计机构、方法说明 | 减少对单一发布方的依赖 |

本地计划把查询标为 `primary_source`、`independent_check` 或 `contradiction_search`。生产计划还应记录地区、日期范围、查询预算、预期来源类型，以及继续查询可能增加什么信息。查询多样化提高召回率，本身不会提高置信度。

## 14.3 来源筛选、去重与提取

### 14.3.1 先筛选，再计数

候选来源应按相关性、对特定主张的权威性、与事件的距离、日期、透明度和独立性排序。权威性依主张而变：交通报告可证明自己发布过什么数字，独立仪表审计则更适合判断修正值。供应商文章可帮助发现术语，却不能排在公开方法和测量数据的记录之前。

仅把归一化内容指纹一致视为重复证据；规范 URL 只用于将候选版本分组并检查，不能单独作为去重键。把镜像 URL 保留为别名。同一内容的报告被转载十次，仍是一个来源，不是十个独立佐证；但同一规范 URL 下经修订或含矛盾证据的内容必须保留为独立版本。Fixture 最终筛选三个记录：

| 来源 | 角色 | 筛选结果 |
| --- | --- | --- |
| 运营报告 | 原始报告基线与结果 | 保留 |
| 运营报告镜像 | 字节等价的重复项 | 合并为别名 |
| 仪表审计 | 独立测量检查 | 保留 |
| 方法说明 | 样本与设计限制 | 保留 |
| 供应商文章 | 宣传性内容，无公开数据 | 排除出证据集 |

### 14.3.2 提取最小、可验证的证据

不能把整页复制进笔记后就称为证据。应提取能支持或反驳一个主张的最小段落，并保存定位和来源 ID：

```python
@dataclass(frozen=True)
class EvidenceItem:
    evidence_id: str
    claim_id: str
    source_id: str
    stance: Literal["supports", "contradicts"]
    quote: str
    locator: str
```

来源标题、规范 URL、发布者、发布日期、内容哈希和别名 URL 单独保存。本地 Fixture 在账本接纳前把引文与不可变的 `RawDocument.content` 重新关联：先折叠空白并忽略大小写，确认引文确实出现；再要求定位采用 `chars:start:end`，且该原始字符区间归一化后与引文完全相同。空引文、虚构引文、非法区间或区间内容不匹配都会产生一个被拒绝的 `ExtractDisposition`，不能进入账本，也不能满足主张覆盖。

通过这一检查只能证明被选来源含有这些文字；来源认证、文档版本与解释仍需检查。网页文本属于不可信数据：检索页面中嵌入的指令不能改变范围、Tool 权限或停止策略。

## 14.4 主张—证据账本与矛盾

### 14.4.1 主张门

主张—证据账本是系统中心：

| 主张 | 支持 | 反证 | 状态 | 动作 |
| --- | --- | --- | --- | --- |
| 能耗低于基线 | 报告 + 审计 | 无 | `supported` | 带 `[1][2]` 纳入 |
| 降幅恰好为 25.0% | 报告 | 审计称 18.3% | `contested` | 连同双方引用呈现分歧 |
| 样本为两条线路的 20 辆车 | 方法说明 | 无 | `supported` | 作为限制纳入 |
| 维护成本下降 | 无 | 无 | `unsupported` | 综合前拒绝 |

门控规则很简单：没有支持证据的主张不能进入产物。争议主张只有在分歧本身与答案有关，且双方证据都可见时才能进入。不可变的 Evidence ID 才是关联键，散文式摘要不能替代它。

### 14.4.2 保留矛盾并校准置信度

不能把互不兼容的段落求平均，也不能悄悄选择最符合草稿的来源。应记录差异发生在哪个维度：总体、日期、定义、方法、版本或数值；再检索修正、后续版本或方法解释。冲突仍存在时，就如实报告。

置信度属于单个主张，不属于整份文档。Fixture 为变化方向给出 `0.93`，因为两个筛选来源一致；为精确幅度给出 `0.52`，因为两者冲突；为单一方法来源直接支持的样本限制给出 `0.81`；为无支持的成本主张给出 `0.0`。这些数值是确定性教学策略，不是统计校准后的概率。生产置信度需要标注评估和校准曲线。

## 14.5 综合与引用

### 14.5.1 从账本综合

草稿应从通过门控的账本行生成，不能从原始搜索片段或模型记忆生成。Fixture 的答案刻意保持窄范围：

> Meridian 的 2025 年试点工作日能耗低于基线 [1][2]。精确降幅仍有争议：现有记录分别意味着 25.0% [1] 和 18.3% [2]。样本仅覆盖两条线路的 20 辆车 [3]，因此证据不能证明全市效果。

这个答案分开处理方向、幅度和可推广性。账本没有维护成本的支持证据，所以答案不提维护成本下降。

### 14.5.2 引用是可验证的关联

只有同时满足以下条件，引用才正确：来源蕴含邻近主张、定位可以解析、来源元数据稳定、编号映射到一个去重后的来源。验证应检查：

- **覆盖：** 每个重要事实主张至少有一个证据关联；
- **正确：** 引用段落以所声明的强度支持该主张；
- **位置：** 读者能判断引用对应哪个句子；
- **溯源：** 引用编号、Source ID、URL 与账本项精确关联；
- **矛盾：** 陈述分歧时同时引用对立证据。

引用数量不等于证据质量。一个直接的一手记录可能比许多派生文章更有证明力。

## 14.6 停止与验证

### 14.6.1 因明确理由停止

Agent 在每轮检索后判断是否停止：

```text
if 所有候选主张均已评估且引用验证通过:
    stop = coverage_satisfied
elif queries_run >= query_budget:
    stop = query_budget_exhausted
elif 上一轮没有新增筛选来源或证据:
    stop = source_saturation
else:
    stop = continue_search
```

`coverage_satisfied` 不表示世界已被完全了解，而表示范围内每个必需主张均已获支持或被如实表述为争议，排除主张已明确拒绝，且引用验证通过。必需主张若缺少支持，仍然是未解决要求，不能因为状态枚举已穷尽而消失。当未解决要求存在且检索预算仍可产生信息时，Agent 应继续检索；预算耗尽或来源饱和时，应暴露未解决 ID 并请求人工介入。引用验证失败也会阻止成功完成。“答案感觉完整”不是停止理由。

### 14.6.2 验证产物，而非相信 Agent 的自信

发布前重新执行来源关联，并强制硬门：纳入的无支持主张为零、孤立引用为零、被折叠的已知矛盾为零、每个重复簇只有一个规范记录。Fixture 将综合结果先保存为明确命名的 `diagnostic_draft`，供失败诊断使用；它不是可发布结果。只有引用验证通过且停止原因为 `coverage_satisfied` 时，公开的 `final_artifact` 与 UI 中的最终产物才非空。验证失败、继续检索、预算耗尽或来源饱和时，所有最终产物表面都保持为空。

再分别评估答案相关性、主张覆盖率、引用蕴含、来源质量、矛盾召回、校准、延迟和搜索成本。流畅答案只要包含一个虚构主张，就应判定失败，不能被平均分掩盖。

## 14.7 Pi 兼容研究 Loop

### 14.7.1 文件、Tools、笔记与压缩

本章唯一实践主线是 Pi 兼容概念：

```text
读取任务与账本文件
→ 选择下一次搜索/阅读步骤
→ 调用获准 Tool
→ 把来源元数据和引文写入笔记
→ 评估主张，并在需要时压缩上下文
→ 验证引用，决定停止/继续
```

Pi Coding Agent 提供最小编码 Loop，以及读取、写入/编辑和 Bash 等内置文件与 Shell 能力。可用工作区 Markdown 或 JSON 作为计划、来源记录、主张账本和检查点的持久笔记。Context Compaction 让长会话继续运行，但压缩摘要不是证据；稳定 ID 与引文必须保留在文件中，以便重新读取和验证。`SKILL.md` 可以封装研究说明和验证步骤，但 Skill 不会让检索到的事实自动变真。

### 14.7.2 Pi 默认不提供什么

Pi 默认**不提供**专用网页搜索引擎、图形浏览器、爬虫、付费数据库订阅、PDF/OCR 管线、向量数据库或引用管理器集成，也不会把笔记文件变成经过认证的溯源存储。只通过经过审查的扩展/自定义 Tool 或获准命令行程序添加任务所需能力，并明确其提供商、权限、限制和失败模式。本章本地 Fixture 不提供这些能力，也不发起网络请求。

这个边界很关键：“Agent 使用了 Pi”并不能说明来源由哪个搜索索引、浏览器、解析器或授权语料库产生。提供商溯源必须写入来源账本。

## 14.8 Agentic UI 状态

界面应展示研究状态，而不是先显示旋转动画，最后突然给出一段文字：

| 可见区域 | 必需内容 | 人工介入 |
| --- | --- | --- |
| 计划 | 范围问题、排除项、子问题、查询预算 | 编辑范围或批准计划 |
| 当前步骤 | 活跃子问题、查询/Tool、耗时、上次结果 | 暂停或取消 |
| 来源 | 保留/拒绝/重复状态、发布者、日期、URL | 打开来源或质疑筛选 |
| 主张支持 | 主张、支持 ID、反证 ID、置信度 | 删除、缩窄或请求更多证据 |
| 不确定性 | 缺失证据、未解决冲突、已知限制 | 继续检索或接受限制 |
| 人工介入 | 精确问题、阻塞原因、每个选择的影响 | 回答、提供来源、修改预算、停止 |
| 最终产物 | 答案、行内引用、来源表、拒绝主张、停止理由 | 导出或重新打开研究 |

建议任务状态为 `needs_scope`、`planned`、`searching`、`extracting`、`assessing`、`needs_intervention`、`synthesizing`、`verifying` 和 `complete`。只有引用验证完成且决策为成功的 `coverage_satisfied` 时，`complete` 才有效。UI 必须保留已选、已拒绝和重复候选项的处置状态，暴露被拒绝主张与停止理由，并在仍需检索或人工介入时不展示“最终产物”状态。陈旧或有争议的证据必须明确标识，不能只依赖颜色。

## 14.9 确定性垂直切片

### 14.9.1 运行方式

`code/go-agentic/14-deep-research-agent/` 下的 Fixture 只使用 Python 标准库：

```bash
python3 -m pytest code/go-agentic/14-deep-research-agent/test_research.py -q
python3 -m pytest code/go-agentic -q
```

测试覆盖计划范围、查询多样化、精确重复与同 URL 变更版本处理、真实引文与字符定位验证、虚构引文和非法定位拒绝、主张支持、无支持主张拒绝、删除/重排来源时仍安全的综合、矛盾保留、动态引用输出与验证、诊断草稿与最终产物隔离、真实 UI 字段和所有停止理由。`.example` 文档是固定数据，任何断言都不依赖实时搜索排序。

### 14.9.2 语义与限制

```python
agent = build_fixture_agent()
result = agent.run(FIXTURE_QUESTION)

assert result.assessment("energy-direction").status == "supported"
assert result.assessment("exact-magnitude").status == "contested"
assert result.assessment("maintenance-cost").status == "unsupported"
assert result.stop.reason == "coverage_satisfied"
assert result.final_artifact == result.diagnostic_draft
```

这是可执行证据契约，不是 Pi SDK、搜索提供商、浏览器、爬虫、解析器或生产研究实现。生产系统还需要来源认证与版本、合规检索、持久存储、访问控制、隐私与版权政策、Prompt Injection 防御、解析器一致性测试、监控和人工复核。

## 14.10 验收指标与练习

### 14.10.1 发布门

| 维度 | 指标 | 本地门槛 |
| --- | --- | --- |
| 计划 | 必需子问题和查询策略齐全 | 100% |
| 来源 | 重复项泄漏到引用表 | 0 |
| 主张 | 产物中的无支持主张 | 0 |
| 证据 | 纳入主张具有有效账本关联 | 100% |
| 冲突 | 已知矛盾得到保留和引用 | 100% |
| 引用 | 蕴含、位置与 Source ID 关联 | Fixture 上 100% |
| 停止 | 每次运行都有命名终止理由 | 100% |

真实 Benchmark 应在调参前冻结问题与来源快照。报告各类别失败和人工裁决，不能只报告一个总分。

### 14.10.2 练习与掌握标准

1. 先写失败测试，再加入一份取代审计结论的带日期修正版，同时保留版本历史。
2. 加入 URL 不同但归一化内容相同的两个页面，证明它们只产生一个引用和两个别名。
3. 加入一个仅有宣传文章支持的主张，定义并测试来源质量门。
4. 让 `source_saturation` 携带未解决 Claim ID 请求人工介入。
5. 构建引用验证器，识别“来源真实但引用到了错误句子”的情况。

当你能展示 RED 再到 GREEN、把每个纳入主张追溯到引文与来源、解释每个拒绝主张、保留分歧而不把它洗成确定性、指出哪些 Web 能力来自 Pi 外部，并说明最终停止理由时，就达到了本章掌握标准。

## 14.11 本章小结

证据驱动的研究 Agent 通过关联关系和停止条件赢得信任。范围定义可回答内容；拆解与查询多样化寻找正确证据；来源筛选与去重保护独立性；提取生成可验证记录；主张账本控制综合；矛盾处理与置信度表达限制；引用把正文连接回来源；明确停止防止无休止或过早搜索。Pi 兼容的文件、Tools、笔记、Skills 与压缩可以承载这条 Loop，而浏览器、搜索、解析和研究数据库仍是需要明确命名的外部能力。

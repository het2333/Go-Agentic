# 第二章 智能体发展与现代运行时

智能体不是 LLM 时代突然出现的概念。符号系统、专家系统和强化学习早已研究“一个系统如何根据环境选择行动”。现代变化在于：语言模型提供了通用的语言决策接口，工具调用把决策连接到软件，Harness 与 Runtime 则让循环能够被控制、记录和持续运行。

学完本章，你应能：

- 说出符号主义、专家系统、强化学习和 LLM Agent 各自留下的核心思想；
- 解释 ELIZA 为什么能产生对话感，却不具备现代 Agent Loop；
- 说明工具调用、上下文窗、Harness 和 Runtime 如何形成现代技术栈；
- 把 Pi 放在 Model—Harness—Runtime—Environment 分层中，而不把产品能力归给模型。

## 2.1 一条有选择的历史线

### 2.1.1 符号、搜索与专家系统

早期符号主义把智能行为表示为符号结构与规则操作。Newell 与 Simon 的“物理符号系统”观点强调：问题求解可以被描述为状态、操作和搜索。这一传统留下了今天仍重要的工程习惯：显式表示状态、约束可用操作、记录决策路径。

ELIZA 使用关键词、分解规则和重组模板产生对话。其核心可以压缩为：

```text
读取输入
→ 找到最高优先级关键词
→ 用规则匹配句式
→ 套用回复模板
→ 若无匹配则返回通用回复
```

它的价值在于展示了少量规则如何产生强烈的交互印象；它的边界也同样清楚：没有开放环境、工具行动、结果验证或面向目标的持续状态。把“像在对话”误判为“理解并完成任务”，正是 Weizenbaum 在原始论文和后续讨论中提醒的问题。

专家系统把符号规则用于狭窄专业领域。DENDRAL 将化学知识和候选搜索结合，MYCIN 则用规则和不确定性权重辅助感染诊断。它们证明了领域知识与解释链的价值，也暴露了知识获取成本高、规则脆弱和跨领域迁移困难。现代 Agent 的工具 Schema、策略规则和安全检查仍继承了“把关键约束显式化”的思想。

### 2.1.2 强化学习：从规则到交互

强化学习把问题写成 Agent 与 Environment 的序贯交互：

```text
state s_t → action a_t → reward r_(t+1), state s_(t+1)
```

策略根据状态选行动，环境返回新状态和奖励。Q-learning 展示了如何从交互经验学习动作价值；AlphaGo 把策略网络、价值网络和树搜索结合，在明确规则和奖励的围棋环境中取得突破。

这条路线为现代 Agent 留下三点：

1. 当前行动会改变未来可见状态；
2. 评价应针对完整轨迹，而不只看单次输出；
3. 探索必须受环境、奖励和预算约束。

LLM Agent 通常不会在每个用户任务中在线更新模型权重，但它同样在轨迹中根据 Observation 调整后续 Action。这里的“学习”多是上下文内适应，不应与训练过程混为一谈。

### 2.1.3 LLM Agent：语言成为决策接口

Transformer 让模型能够在上下文中处理长距离依赖；大规模语言建模进一步带来了指令跟随、少样本适应和代码生成能力。ReAct 等工作把推理轨迹与环境行动交错组织，使语言模型可以在任务中查询外部信息，再根据返回结果继续决策。

关键变化不是模型获得了操作系统权限，而是软件系统可以：

- 用消息向模型描述目标、工具和当前观察；
- 接收文本或结构化工具请求；
- 在宿主程序中执行请求；
- 把工具结果作为新消息送回模型；
- 用验证、预算和批准规则决定是否继续。

因此，现代 Agent 是模型能力与系统工程共同产生的结果。

## 2.2 现代技术栈为何形成

### 2.2.1 Tool Calling 连接语言与行动

工具调用让模型输出“调用哪个工具、使用哪些参数”的结构化意图。真正的执行者始终是 Harness 或应用程序。它必须校验工具名和参数、检查权限、执行代码，并返回可观察结果。


不同提供商的消息角色、Schema 子集、并行调用和错误格式并不完全相同。Framework 或 Provider Adapter 可以统一部分差异，但应用仍需测试自己的边界。

### 2.2.2 Context Window 形成工作状态

LLM 每次只根据当前请求中的上下文生成结果。系统指令、用户目标、工具定义、历史消息和工具输出都占用上下文窗。窗口扩大后，Agent 能携带更长轨迹；但无关日志、陈旧假设和冲突指令也会一起进入决策。

因此出现了上下文选择、摘要压缩、会话分支和外部记忆。上下文窗是有限输入预算，不是可靠数据库；缓存是重复前缀的计算优化，也不是记忆。本课程在第 8–9 章展开这些能力。

### 2.2.3 Harness 与 Runtime 把调用变成系统

一次“模型 → 工具 → 模型”只是一轮交互。Harness 加入循环、工具注册、观察封装、验证、错误处理、审批和轨迹日志。Runtime 再负责会话持久化、进程生命周期、资源、并发、恢复和用户界面。

| 层 | 典型状态 | 典型失败 |
| --- | --- | --- |
| Model / Provider | 消息、采样参数、模型响应 | 超时、限流、无效结构 |
| Harness | 工具表、Loop 状态、预算、验证结果 | 错误分派、无限循环、误判完成 |
| Runtime | 会话、进程、持久化、并发资源 | 崩溃、恢复失败、状态冲突 |
| Environment | 文件、测试、浏览器、业务 API | 权限拒绝、数据变化、工具错误 |

这种分层能定位责任：模型选错工具和工具执行失败是两类问题；Harness 没有停止预算与模型偶尔重复行动也是两类问题。

## 2.3 当代实例：Pi 的边界

### 2.3.1 为什么作为课程主线

Pi 官方将其 coding agent 描述为“minimal terminal coding harness”。其默认工具为 `read`、`write`、`edit` 和 `bash`，并通过 Sessions、Branching、Compaction、Skills、Extensions 与 Packages 扩展。官方仓库还把多提供商模型 API、Agent Core 和交互式 Coding Agent CLI 分成独立包。

这些是项目事实；“Pi 适合从最小 Loop 逐章学习”是 Go Agentic 的教学选择。课程不会把第三方扩展描述为 Pi 核心能力，也不会把 Pi、DeepSeek Harness 和 Hermes 写成三条平行教程。

### 2.3.2 登录故障在栈中的流动

放入现代栈后，第一章的轨迹仍将每项责任分配给独立层次。


模型或假策略负责提出下一步；Harness 负责执行与控制；仓库和测试进程构成环境；测试通过是验证证据。这个责任划分将在后续章节保持不变。

## 2.4 用一条运行轨迹重读历史

把不同历史路线放到同一个循环的不同位置，它们的工程贡献会更具体：

| 循环阶段 | 继承的能力 | 需要保留的工程边界 |
| --- | --- | --- |
| Observe | 符号系统让任务状态和可用 Operator 显式化 | 表示无法覆盖设计者没有编码的信息 |
| Decide | 搜索、学习得到的价值估计与语言模型提供不同的下一步选择方式 | 看似合理的选择仍需受权限约束 |
| Act | 模板、领域流程与类型化 Tool Call 把选择变成操作 | 真正执行属于宿主系统与 Environment |
| Verify | Reward 可以评价轨迹；现代任务系统还可检查测试、查询、批准或后置条件 | 训练 Reward 与运行时证据回答不同问题 |

设想一个 Agent 正在分诊夜间库存导入失败。它先观察错误码和受影响的 Batch ID。符号规则把错误归入 Schema 类别，学习型 Ranker 对候选原因排序，语言模型再决定调用哪个有界诊断 Tool。Harness 执行只读 Schema 比较，把不一致作为新 Observation 返回。修复获得授权并执行后，独立的行数与 Checksum 查询验证导入结果。没有哪条历史路线独占整条轨迹；每种方法都在一个可检查的边界上发挥作用。

这种视角还能避免常见的类别混淆：训练时更新 LLM 权重、根据当前 Context 选择 Action，以及验证外部后置条件，是三种不同机制，即使它们都使用反馈。

## 2.5 本章小结

- Agent 的历史主线是“表示状态—选择行动—读取环境反馈”，LLM 改变了决策接口和适用范围。
- ELIZA 是规则驱动对话程序，不具备开放工具、验证与目标循环。
- 专家系统贡献了显式知识，强化学习贡献了序贯交互和轨迹评价。
- Tool Calling、Context Window、Harness 与 Runtime 共同构成现代 Agent 栈。
- Pi 是本课程的唯一实践主线，其项目事实以官方仓库为准。

## 掌握标准

当你能用一条连贯历史线解释符号规则、环境交互和语言决策的继承关系；能把一个现代 Agent 产品准确拆到 Model、Harness、Runtime 和 Environment；并能判断故障属于哪一层时，即达到本章要求。

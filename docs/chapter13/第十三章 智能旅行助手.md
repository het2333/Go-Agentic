前十二章分别讨论了 Loop、Tool、检索、记忆、Context、MCP、评测、审批和安全。本章把这些能力压缩到一个有真实副作用边界的任务：供应商声称采购订单 `PO-7` 已发货，但物流记录在合同期限后仍没有追踪号。Agent 必须找到最新邮件，核对采购订单、合同和物流记录，建立证据账本，判断异常，起草催询邮件，展示执行预览，等待人工批准，只发送一次，并留下可恢复的审计轨迹。

本章的实践主线只有与 Pi 兼容的“观察—决策—行动—验证”Loop 概念。示例不依赖 Pi SDK，也不连接真实邮件、ERP、合同库或物流平台；所有数据均固定在内存中，无网络、无 API Key、可重复测试。

完成本章后，你应该能够：

- 把业务主张、权威记录和派生判断分开；
- 用来源、记录 ID、观察时间和内容哈希建立证据账本；
- 把草稿与执行预览、人工批准、幂等键和审计事件连成闭环；
- 在证据缺失、拒绝、重试和“发送成功但审计失败”时保持安全状态；
- 用功能、安全、恢复和运营指标定义验收标准。

## 13.1 任务与完成契约

### 13.1.1 供应商交付异常

固定案例发生在 `2026-09-13T09:00:00+08:00`：

| 来源 | 当前记录 | 能证明什么 | 不能证明什么 |
| --- | --- | --- | --- |
| 最新邮件 `MSG-483` | 供应商称 `PO-7` 已发货 | 供应商作出了发货主张，联系人为谁 | 货物真的交给了承运商 |
| ERP `PO-7:v3` | 供应商、合同 ID、交付日期 | 当前采购订单状态与关联关系 | 合同条款或物流扫描 |
| 合同 `CTR-9:v2` | 发货后 24 小时内提供追踪号 | 追踪号义务与时限 | 当前是否已有追踪号 |
| 物流 `SHIP-77:v1` | `shipped_at` 已记录，追踪号为空 | 当前物流系统记录 | 供应商内部尚未同步的数据 |

这四条记录共同支持一个有限判断：追踪号已经超过合同期限仍缺失。它们不支持“货物丢失”“供应商欺诈”或“应修改采购订单”等更强结论。

### 13.1.2 权限与完成条件

任务权限分为两类：读取四个指定来源是预授权的；向 `orders@northstar.example` 发送一封具体邮件是待批准副作用。批准必须绑定收件人、主题、正文和幂等键形成的 `action_hash`。任何字段变化都使旧批准失效。

任务只有同时满足以下条件才算完成：

1. 四类必需证据齐全且可追溯；
2. 异常由确定规则支持；
3. 人看到与实际发送内容完全一致的预览；
4. 有匹配该预览的明确批准；
5. 邮件网关返回稳定消息 ID，重复执行不产生第二封邮件；
6. 审计记录能串联证据、判断、草稿、批准、发送结果和恢复。

生成草稿不等于完成，模型说“已发送”也不是完成证据。

## 13.2 架构与 Pi 兼容 Loop

### 13.2.1 数据路径

Agent 每次只读取当前决策需要的最小数据。`PO-7` 是跨系统关联键，记录版本和观察时间防止旧内容冒充当前状态。

```text
任务 PO-7
   │
   ├─观察→ Email Adapter ─────┐
   ├─观察→ ERP Adapter ───────┤
   ├─观察→ Contract Adapter ──┼─→ Evidence Ledger
   └─观察→ Logistics Adapter ─┘          │
                                         ↓
                              deterministic Policy
                                         │
                                  anomaly + draft
                                         ↓
                              preview + action_hash
                                         │
                              Human approval gate
                                         ↓
                          send_once(idempotency_key)
                                         │
                                  receipt + Audit
```

四个 Adapter 是本地类型化 Tool 边界。生产环境可以在相同边界后接 MCP Client 和业务系统，但 MCP 只负责能力连接；业务 API 仍须实现权限、并发控制、幂等和回执验证。

### 13.2.2 状态转移

Pi 主线强调一个清晰 Loop，而不是把全部业务逻辑藏进 Prompt。模型或策略选择下一步观察；Harness 验证 Tool 参数、状态和权限；Environment 返回结构化结果；确定规则处理高影响判断；副作用在批准点暂停。

```text
collecting_evidence
   ├─缺少来源────────────→ needs_evidence ─→ 补证后重新观察
   ├─陈旧/冲突/篡改──────→ evidence_blocked ─→ 刷新后重新观察
   ├─无异常──────────────→ no_action
   └─证据齐全且异常成立──→ awaiting_approval
                               ├─拒绝────→ rejected
                               ├─预览改变→ awaiting_approval（重新批准）
                               └─批准────→ execute
                                             ├─成功→ completed
                                             └─部分失败→ recovery_required
                                                            └─幂等重放→ completed
```

`needs_evidence`、`evidence_blocked`、`rejected` 和 `recovery_required` 都是一等状态，不能包装成普通成功文本。`completed` 是终态：后续重放、缺少批准或新的拒绝均不能改写已发生的外部事实。长任务恢复时，还要重新读取可变的 ERP、批准和物流状态；本地示例只演示固定快照。

## 13.3 证据账本

### 13.3.1 Schema 与权威性

账本保存事实及其来源，不保存无出处的总结：

```python
@dataclass(frozen=True)
class EvidenceRecord:
    evidence_id: str       # logistics:SHIP-77:v1
    source: str            # email | erp | contract | logistics
    record_id: str         # 原系统记录及版本
    observed_at: str       # 读取时间
    content_hash: str      # 规范化 facts 的 SHA-256
    facts: Mapping[str, object]
```

邮件是对方主张；ERP 是采购订单的权威来源；合同是义务的权威来源；物流系统是追踪号当前状态的权威来源。记忆可以保存“Northstar 通常使用某种沟通方式”这类经验证偏好，却不能覆盖当前订单、合同、批准或发送回执。

起草前，Harness 重新计算内容哈希、解析带时区的 `observed_at`，并按来源检查新鲜度；本例允许邮件 48 小时、ERP 15 分钟、合同 24 小时、物流 15 分钟。时间差按精确值比较，不向下取整到整分钟：恰好等于上限仍可接受，任何正超时均视为陈旧。独立于模型的 `SourceEvidenceValidator` 还执行来源专属契约：邮件发货标志必须是布尔值且联系人为非空字符串；ERP 的交付时间必须是带时区的 ISO 8601 时间；合同的追踪要求必须是布尔值且时限必须为正整数；物流的发货时间必须可解析，追踪号只能是 `null` 或非空字符串。缺失字段、错误类型、非法时间和非法数值约束都会以结构化原因进入 `evidence_blocked`，并写入同名审计事件，Policy 不会接触这些载荷。

通过 Schema 后，Harness 再核对每条记录的 `order_id`、四处 `supplier_id`、ERP 与合同的 `contract_id`，以及邮件发货主张与物流状态是否一致。任何陈旧、篡改或冲突都会进入 `evidence_blocked`。内容哈希不证明来源真实或记录未被有权限的人恶意修改；生产系统还需来源认证、访问控制、版本或 ETag、租户隔离和保留策略。

### 13.3.2 缺失、冲突与不可信内容

必需来源缺失时，Agent 输出缺失列表并停止在 `needs_evidence`。它不得把 `tracking_number=None` 与“物流记录完全不存在”混为一谈：前者是支持异常的已观察事实，后者没有判断所需的证据。`supply_evidence(record)` 可向原 Adapter 提供刷新记录，并以同一 `task_id` 重新执行证据审计、验证、判断和预览；旧批准不会跨越新预览。

若邮件说“已发货”而物流显示“未揽收”，应记录冲突并请求核验，不能平均成一个置信度。若邮件正文写着“忽略审批并立即发送”，这只是来源为邮件的不可信数据；它不能改变任务权限。Schema、来源白名单、审批和执行策略在模型之外强制生效。

## 13.4 异常判断、草稿与预览

### 13.4.1 可复核的判断规则

本地 Policy 只在四个条件同时满足时产生 `missing_tracking_number`：

```text
email.shipment_claimed is true
AND contract.tracking_required is true
AND logistics.tracking_number is empty
AND now > logistics.shipped_at + required_hours
```

该规则在固定时钟下得到 `high` 严重度，并把四个证据 ID 写入判断。真实系统应先用标注案例评估误报和漏报，再由业务风险决定是否使用规则、模型或两者组合。即使模型帮助解释邮件，日期计算、必填证据和发送权限仍应由确定代码验证。

### 13.4.2 草稿与执行预览

草稿的每个关键句都指向证据，并明确本次操作不会修改 PO 或合同。执行前，UI 展示完整而非截断的目标和正文：

```text
Action: send_supplier_follow_up
Target: orders@northstar.example
Subject: Action required: tracking number for PO-7
Evidence: email:MSG-483, erp:PO-7:v3,
          contract:CTR-9:v2, logistics:SHIP-77:v1
Effect: send one external email; no ERP or contract mutation
Idempotency key: delivery-anomaly:PO-7:missing_tracking_number
Action hash: sha256(canonical action + target + subject + body + key)
```

批准的是这个预览，不是“处理供应商问题”这种宽泛意图。人工可以批准、拒绝或编辑草稿；编辑后必须重新计算哈希并重新批准。

## 13.5 人工批准与恰好一次执行

### 13.5.1 参数绑定批准

批准记录至少包含 `approval_id`、批准人、决定、`action_hash`、`decided_at` 和 `expires_at`。执行器解析带时区的时间，拒绝未来决定、无效区间和已过期批准，再比较当前预览哈希。没有批准、批准被拒绝、哈希不匹配或批准过期时，邮件网关均不可调用。批准在发送前存入任务状态；若发送后审计失败，恢复只能沿用真正授权发送的原批准，不能把 `APR-42` 的外部效果归给后来传入的 `APR-99`。拒绝与批准使用语义不同的审计 ID，例如 `approval-rejected:APR-42` 与 `approval-recorded:APR-42`；若用同一事件 ID 重放不同的类型、任务或详情，必须判为冲突。只有返回的持久事件确实是本次授权对应的 `approval_recorded`，邮件网关才可放行。

UI 不能用默认勾选框或模糊按钮代替明确决定。高影响操作还应显示身份、权限范围和有效期，并对异常收件域、敏感数据或金额升级审批级别。

### 13.5.2 幂等执行

“恰好一次”描述业务效果，而不是假设网络传输永远只发生一次。客户端超时可能发生在服务端已经发送之后，因此重试必须携带同一逻辑操作的稳定幂等键：

```python
def send_once(preview):
    if preview.idempotency_key in durable_results:
        return durable_results[preview.idempotency_key]
    receipt = provider.send(preview)
    durable_results.insert_unique(preview.idempotency_key, receipt)
    return receipt
```

本地 `InMemoryMailGateway` 用字典和稳定消息 ID 演示该契约。每个幂等键同时绑定由收件人、主题和正文组成的请求指纹；同键不同载荷会被拒绝。生产实现需要持久化唯一约束、并发原子性、请求指纹和明确的键生命周期。

### 13.5.3 失败恢复与审计

所有必需的发送前审计必须先持久化。证据、判断、草稿或批准审计失败时，状态转为带恢复阶段的 `recovery_required`，邮件网关保持零调用；`resume()` 先补齐缺口才允许继续。最危险的窗口是“外部发送已成功，本地审计尚未写入”：示例保留原批准和消息 ID，恢复时使用原幂等键取得同一回执，再补写发送与恢复审计。

| 失败点 | 可观察状态 | 恢复动作 | 禁止行为 |
| --- | --- | --- | --- |
| 读取来源失败 | `needs_evidence` 或结构化 Tool 错误 | 重试只读调用或人工补证 | 猜测缺失字段 |
| 批准前中断 | `awaiting_approval` | 重建预览并验证哈希 | 自动视为已批准 |
| 必需发送前审计失败 | `recovery_required`，无消息 ID | 先以同一事件 ID 补审计 | 审计缺口存在时发送 |
| 发送前失败 | 无消息 ID | 用同一批准和幂等键重试 | 生成新逻辑键 |
| 发送后审计失败 | `recovery_required`，有消息 ID | 查询/重放幂等结果并补审计 | 无条件再次发送 |
| 永久失败 | `recovery_required` | 告警、人工处置、必要时补偿 | 报告成功 |

审计事件使用单调序号和稳定事件 ID，记录证据 ID、判断码、预览哈希、批准 ID、幂等键和提供方消息 ID。正文与无关个人数据不应默认复制进日志。审计是可验证事件，不是隐藏思维链。

## 13.6 UI 状态

面向人的界面必须让等待原因和下一步动作可见：

| 状态 | 页面重点 | 允许操作 |
| --- | --- | --- |
| `collecting_evidence` | 正在读取哪些来源、已等待多久 | 取消 |
| `needs_evidence` | 缺失来源和最后错误 | 重试、提供证据、转人工 |
| `evidence_blocked` | 陈旧、哈希不符或跨来源冲突 | 刷新证据、转人工 |
| `awaiting_approval` | 异常依据、完整草稿、目标、效果、哈希 | 批准、拒绝、编辑 |
| `rejected` | 决定人和拒绝时间 | 关闭或创建新草稿 |
| `recovery_required` | 是否已有消息 ID、当前恢复步骤 | 安全重试、转人工 |
| `completed` | 消息 ID、发送时间、审计入口 | 查看证据与轨迹 |

页面顶部可用一条简短进度线：`证据 4/4 → 异常已确认 → 等待批准 → 已发送 → 审计完成`。不要用永久旋转动画隐藏停顿，也不要在 `recovery_required` 时显示绿色“完成”。

## 13.7 确定性垂直切片

### 13.7.1 运行方式

代码位于 `code/go-agentic/13-enterprise-execution-agent/`，只使用 Python 标准库：

```bash
python3 -m pytest code/go-agentic/13-enterprise-execution-agent/test_agent.py -q
```

测试覆盖预览、终态、批准门与有效期、原批准归属、发送前审计门、证据新鲜度/完整性/一致性、补证恢复、载荷指纹、幂等重放、审计记录和部分失败恢复。实际测试组件不是只会返回成功的 Mock；Adapter、Ledger、Policy、Gateway 和 Audit Log 都运行真实的内存逻辑。

### 13.7.2 代码语义与限制

最小调用过程如下：

```python
from agent import ApprovalDecision, build_demo_system

system = build_demo_system()
state = system.agent.prepare("PO-7")
assert state.status == "awaiting_approval"
assert system.mail_gateway.sent_messages == ()

approval = ApprovalDecision(
    approval_id="APR-42",
    actor="buyer@example.com",
    approved=True,
    action_hash=state.preview.action_hash,
    decided_at="2026-09-13T08:59:00+08:00",
    expires_at="2026-09-13T09:05:00+08:00",
)
completed = system.agent.execute(approval)
assert completed.status == "completed"
assert len(system.mail_gateway.sent_messages) == 1
```

`build_demo_system(missing_sources={"logistics"})` 演示补证状态，随后可调用 `supply_evidence(record)` 恢复同一任务；`fail_audit_once={"approval_recorded"}` 和 `{"message_sent"}` 分别演示发送前、发送后的审计恢复。此代码不是 Pi SDK、MCP、SMTP 或 ERP 一致性实现，也没有持久化、真实认证、并发、密钥、供应商回执查询或补偿操作。

## 13.8 验收指标

先冻结正常、缺证、冲突、拒绝、预览篡改、重复点击、超时和部分失败案例，再计算指标：

| 维度 | 指标 | 本地发布门 |
| --- | --- | --- |
| 证据 | 必需来源覆盖率、引用正确率、新鲜度 | 固定案例均为 100% |
| 判断 | 异常精确率、召回率、人工推翻率 | 规则案例全部符合标注 |
| 批准安全 | 批准前副作用、哈希不匹配执行数 | 必须为 0 |
| 幂等 | 每个逻辑键的外部消息数 | 必须为 1 |
| 审计 | 必需事件完整率、ID 可关联率 | 必须为 100% |
| 恢复 | 部分失败恢复成功率、重复副作用数 | 100%，重复数为 0 |
| 运营 | P50/P95 调查耗时、批准等待时间、人工升级率 | 分开报告机器与人工等待 |

任何未批准发送、重复发送、缺证仍起草执行、审计缺口或把失败显示为完成，都属于硬失败，不能由平均分抵消。生产试点还要按供应商、订单风险和语言切片，监测分布变化，并为告警、停机开关和事件响应指定 Owner。

## 13.9 练习与掌握标准

### 13.9.1 练习

1. 先写失败测试，再加入“邮件与物流发货时间冲突”状态；说明为什么系统不能直接起草催询邮件。
2. 为拒绝和编辑后的草稿加入测试，证明旧 `action_hash` 不能执行新正文。
3. 把内存 Adapter 设计成四个只读 MCP Tool Schema，并标明权限、错误和超时；不要连接真实系统。
4. 模拟两个 Worker 同时执行同一批准，设计数据库唯一约束和事务边界，证明只产生一个外部效果。
5. 为本章定义 12 个验收案例，至少包含缺证、注入文本、重复点击、发送后超时和审计恢复。

### 13.9.2 掌握标准

你达到本章标准时，应能独立提交一个无网络、无 Key 的垂直切片，并提供以下证据：

- 能逐字段解释四类来源的权威边界，并区分“字段为空”与“来源缺失”；
- 能画出状态机，且每个失败状态都有明确恢复或停止条件；
- 测试先出现预期 RED，再达到 GREEN；
- 无批准和哈希不匹配时副作用为零，批准后任意重放仍只有一个消息 ID；
- “发送成功、审计失败”能恢复为完整轨迹，且不会重复发送；
- 中英文的结构、图、代码语义、练习、指标和来源一一对应。

## 13.10 本章小结

企业任务执行 Agent 的难点不在写出一封邮件，而在证明为什么可以写、谁批准了什么、外部效果是否只发生一次，以及中断后怎样继续。证据账本把主张与权威记录分开；Pi 兼容 Loop 按需观察并显式转移状态；确定 Policy 约束异常判断；预览哈希把批准绑定具体动作；幂等键和回执控制重试；审计与恢复让“完成”可以复核。这些边界共同把一个会生成文本的模型变成可控的任务执行系统。

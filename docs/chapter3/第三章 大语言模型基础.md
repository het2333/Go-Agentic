构建 Agent 不要求先掌握完整的预训练数学，但必须知道模型为何会变化、消息怎样进入上下文、工具调用怎样跨越提供商边界，以及上下文、缓存、延迟和成本如何限制 Loop。本章只保留能直接解释 Agent 行为的基础。

学完本章，你应能：

- 用 Token、下一 Token 预测、Attention 和解码解释模型输出；
- 组织 System、User、Assistant 与 Tool 消息；
- 设计并校验 Tool Schema 与结构化输出；
- 计算上下文预算，正确理解 Prompt Cache；
- 定位可观察的模型、协议与 Loop 失败。

## 3.1 足够用的生成基础

### 3.1.1 Token 与下一 Token 预测

语言模型先把文本编码为 **Token** 序列。Token 可能是一个字、词的一部分、标点或空白片段；Token 数不等于字符数或单词数。代码、JSON、路径和中英文混排会产生不同切分，因此上下文预算应使用目标模型的 tokenizer 或 API usage，而不是凭字数估算。

对已有序列 (x_{1:t})，自回归模型估计下一个 Token 的条件概率：

```text
P(x_(t+1) | x_1, x_2, ..., x_t)
```

它反复采样或选择下一个 Token，直到产生停止标记或达到输出上限。模型生成的是条件上最可能的延续，并没有自动查询环境事实。这解释了为什么流畅文本仍可能与仓库、数据库或当前时间不一致。

### 3.1.2 Transformer 与 Attention

Transformer 把 Token 映射为向量，并通过多层 Attention 和前馈网络计算上下文相关表示。对 Agent 工程，记住三件事即可：

1. **顺序需要表示**：位置编码让模型区分 Token 的位置；
2. **Attention 是加权读取**：每个位置从上下文其他位置聚合相关信息；
3. **计算有窗口**：模型只能使用本次请求实际提供且未被截断的内容。

Attention 不保证模型总能找到关键行。长日志中的错误可能被无关输出淹没，彼此矛盾的指令可能竞争，位于窗口外的事实完全不可见。Harness 仍需筛选上下文、突出证据并验证结果。

### 3.1.3 解码参数改变轨迹

模型把 logits 转为 Token 概率。常见解码控制包括：

- **temperature**：调节分布尖锐程度；较低值通常减少变化，但不保证跨请求完全一致；
- **top-p**：只从累计概率达到阈值的候选集合中采样；
- **max output tokens**：限制单次响应长度，过小会截断 JSON 或工具参数；
- **stop condition**：遇到指定序列或协议终止事件时停止生成。

确定性测试不应依赖“temperature=0 一定相同”。提供商实现、模型版本和服务端更新都可能改变结果。第一章使用 Fake Policy，正是为了把 Harness 测试与模型随机性分开。

## 3.2 Messages 与 Provider Boundary

### 3.2.1 消息序列是模型的工作输入

Agent 的一次模型请求通常由以下逻辑内容构成：

| 消息 | 作用 | 例子 |
| --- | --- | --- |
| System / Developer | 定义角色、规则、工具使用约束 | “修改后必须运行相关测试” |
| User | 提供目标和新信息 | “修复登录失败” |
| Assistant | 保存模型先前的回答或工具请求 | `run_tests(...)` |
| Tool | 保存宿主执行后的观察 | `FAIL ... src/auth/login.py` |

模型没有自动持久化的任务状态。多轮交互依赖应用重发或由服务端会话机制重建这些内容。需要长期可靠保存的事实应进入 Runtime 状态、文件或数据库，而不是只留在模型的自然语言回答中。

### 3.2.2 先定义内部协议，再适配提供商

不同模型 API 对角色名称、内容块、工具调用 ID、并行调用、图片输入、Schema 子集和错误响应有不同要求。一个可移植 Harness 应先定义内部类型，再由 Provider Adapter 双向转换。


归一化不能抹去重要信息。停止原因、使用量、缓存命中、工具调用 ID、限流和安全拒绝都应保留为可观察字段。切换模型提供商是边界迁移，需要契约测试，不能只改模型名。

## 3.3 Tool Schema 与结构化输出

### 3.3.1 Schema 描述可选行动

Tool Schema 把工具名、用途和参数约束放入模型上下文。下面的 JSON Schema 与第一章 `read_file` 行动语义一致：

```python
READ_FILE_SCHEMA = {
    "name": "read_file",
    "description": "Read one UTF-8 text file from the allowed workspace.",
    "parameters": {
        "type": "object",
        "properties": {
            "path": {
                "type": "string",
                "description": "Workspace-relative file path.",
            }
        },
        "required": ["path"],
        "additionalProperties": False,
    },
}
```

名称应稳定，描述应说明何时使用，参数应尽量狭窄。把任意 Shell 字符串伪装成“一个工具”会扩大权限和测试空间。Schema 只能约束结构；路径是否越界、用户是否有权限、操作是否安全仍由 Harness 在执行前检查。

### 3.3.2 让一个 Tool Request 依次通过四道门

假设当前 Observation 说明订单 `A-18` 获批的退款上限是 87.00 CNY。模型随后决定请求这个结构有效的 Action：

```json
{
  "tool": "issue_refund",
  "arguments": {
    "order_id": "A-18",
    "amount_minor": 870000,
    "currency": "CNY"
  }
}
```

JSON 解析回答“能否读懂该请求”；Schema 校验检查必填字段、类型与 Currency Enum。两者都不会发现 `870000` 个最小货币单位是已观察批准金额的一百倍。执行前，Harness 必须把请求与订单状态、金额上限、幂等规则和调用者权限比较。它拒绝这个候选 Action，并返回可供下一步决策使用的 Observation：

```json
{
  "ok": false,
  "error_type": "AMOUNT_EXCEEDS_AUTHORIZATION",
  "authorized_minor": 8700,
  "requested_minor": 870000,
  "retryable": true,
  "verified": false
}
```

下一次决策可以修正金额，但“已经执行”仍不等于“已经成功”。获准的退款调用返回 Transaction ID 后，Verification 必须重新读取订单或支付记录，并确认金额、币种、订单 ID 与交易状态。四道门依次是：观察约束事实，决定一个类型化请求，在权限内校验并行动，再验证外部后置条件。

Structured Outputs 加强了 Model 到 Harness 的边界。语义检查与执行仍由 Harness 负责，只有 Environment Evidence 可以设置 `verified=true`。

## 3.4 Context Budget 与 Caching

### 3.4.1 给输入和输出共同留预算

一次请求的上下文占用可以近似写为：

```text
T_total =
  T_instructions + T_tool_schemas + T_history
  + T_tool_results + T_user_input + T_reserved_output
```

`T_total` 必须落在所选模型和 API 的限制内。工程上还要给输出、工具结果增长和提供商计数差异留余量。

| 内容 | 保留原则 | 常见处理 |
| --- | --- | --- |
| 任务边界与安全规则 | 始终可见 | 稳定前缀 |
| 当前计划和最近观察 | 高优先级 | 原文或短结构 |
| 大段工具输出 | 只保留决策证据 | 截取相关区间并保存原始引用 |
| 已完成的旧轨迹 | 保留结论与未决风险 | Compaction |
| 可重新读取的文件 | 按需加入 | JIT Context |

窗口越大不等于内容越多越好。上下文工程的目标是在正确时刻提供足够证据，并让遗漏和压缩过程可追踪。

### 3.4.2 Prompt Cache 是计算优化

提供商可缓存重复的输入前缀，降低后续请求的处理延迟或计费输入。要提高命中率，应把稳定的系统指令和工具 Schema 放在前面，把每轮变化的观察放在后面，并观察 API 返回的缓存 usage。

缓存有三个边界：

- 是否命中、保存多久和如何计费取决于提供商；
- 改动前缀中的任意内容都可能降低命中；
- 缓存不会替你保存任务事实，也不会扩大 Context Window。

因此，Prompt Cache、会话状态、长期记忆和 Compaction 是四个不同概念。

## 3.5 Latency、Cost 与 Provider Choice

### 3.5.1 看完整 Loop 的关键路径

一次 Agent 任务的延迟不只是首个模型响应：

```text
L_task ≈ Σ L_model_calls + Σ L_tool_calls + L_queue + L_retries
```

串行工具调用会累加延迟；可以证明互不依赖的读取才适合并行。缩短无关上下文、限制工具输出、避免重复失败和及早终止，通常比单纯追求更快的单次解码更有效。

若提供商按 Token 计费，可用下式估算模型成本。令 `T_input` 表示总输入 Token，`T_cached` 表示其中命中缓存的子集，并要求 `0 ≤ T_cached ≤ T_input`：

```text
C_model ≈ (T_input - T_cached) × P_input
        + T_cached × P_cached
        + T_output × P_output
```

实际价格、缓存折扣和推理计费以调用时的官方价格页与 usage 字段为准。还应记录搜索、浏览器、数据库和人工审批等工具成本。评估 Agent 时使用“完成一个已验证任务的总成本”，而不是只比较每百万 Token 单价。

### 3.5.2 Provider Boundary 必须可观测

Provider Adapter 至少应暴露：

- 模型标识和可追踪版本信息；
- 请求 ID、停止原因和错误类型；
- 输入、输出与缓存 Token 使用量；
- Tool Call 的原始 ID 与归一化结果；
- 延迟、重试次数、限流和拒绝信息。

模型选择应基于任务集测试：工具调用正确率、长上下文表现、延迟、总成本和可用性。排行榜或营销描述不能替代你自己的轨迹与验证结果。

## 3.6 可观察的失败模式

| 现象 | 所在边界 | Harness 应做什么 |
| --- | --- | --- |
| JSON 无法解析或缺少必填字段 | Model / Provider | 记录原始停止原因，有限次修复或重试 |
| 工具名不存在 | Model → Harness | 拒绝分派，返回允许列表 |
| 参数结构正确但路径越界 | Harness → Environment | 权限校验失败，不执行 |
| 工具超时或返回部分结果 | Environment | 标记错误类型、可重试性和部分证据 |
| 关键失败日志被截断 | Context | 保留原始引用，重新读取相关区间 |
| 相同行动反复出现 | Loop | 检测重复，消耗重试预算后停止 |
| 模型宣布成功但没有证据 | Verification | 返回 `unverified`，继续验证或停止 |
| 切换提供商后工具结果无法关联 | Provider Adapter | 用调用 ID 做契约测试并保留原始响应 |

可观察性不是“打印更多日志”，而是让每个边界的输入、输出、错误和决策能够关联到同一条轨迹。

## 3.7 本章小结

- LLM 通过 Token 序列和下一 Token 预测生成内容；Attention 只处理实际进入窗口的信息。
- 解码参数影响输出分布，不能替代确定性 Harness 测试。
- Messages 构成每次请求的工作输入；持久状态属于 Runtime 或外部存储。
- Tool Schema 约束结构，Harness 负责语义、权限、执行和验证。
- Context Budget、Prompt Cache、Latency 与 Cost 必须按完整 Loop 管理。
- Provider 差异需要 Adapter、契约测试和可观察字段。

## 习题

1. 为第一章完整轨迹列出每轮消息：System、User、Assistant Tool Call 与 Tool Observation，并标明哪些内容可以压缩。
2. 为 `replace_text` 编写 JSON Schema，限制 `path`、`old`、`new` 为必填字符串，并说明 Schema 无法阻止的两个风险。
3. 假设上下文上限为 32,000 Token，固定指令与工具占 6,000，历史占 14,000，最新工具结果占 5,000，计划保留 4,000 输出。计算剩余余量，并提出一次压缩方案。
4. 设计一个包含“无效 Tool Call、工具超时、模型无证据结束”的三步失败轨迹，为每步写出可观察字段和终止判断。

## 掌握标准

当你能从一条真实 Agent 轨迹反推消息、工具 Schema、上下文占用、缓存边界、关键路径延迟和总成本；能把失败定位到 Model、Provider Adapter、Harness 或 Environment；并能说明结构化输出为何仍需语义验证时，即达到本章要求。

# 第六章 Agent 开发生命周期与框架选择

  <figcaption><em>框架选择取决于系统必须支持的生命周期与控制能力。</em></figcaption>
</figure>

Agent 项目不会因为选定模型或 Harness 就自动进入生产。可靠交付需要一串基于证据的门槛：定义任务，设计 Environment，选择 Model 与 Harness，构建最小原型，评估结果与轨迹，加入可观测性，完成安全审查，再以可回滚方式部署。本章给出从想法到运行系统的同一条生命周期主线。

学完本章，你应能：

- 把产品想法写成可评估的任务与权限契约；
- 先设计 Environment 和成功证据，再选择 Model 与 Harness；
- 用能力矩阵和任务集证据记录技术选择；
- 构建包含成功、恢复、拒绝与终止案例的评估集；
- 定义轨迹、指标、安全审查与部署门槛；
- 为上线 Agent 设计版本、灰度、回滚和持续评估。

## 6.1 生命周期是一组证据门槛

### 6.1.1 八个阶段


| 阶段 | 必须产出的 Artifact | 进入下一阶段的证据 |
| --- | --- | --- |
| 任务定义 | 任务契约、样例、成功与停止条件 | 人能独立判断样例是否完成 |
| Environment 设计 | Tool、权限、Fixture、验证器 | Action 可校验，结果可重放 |
| Model 与 Harness 选择 | 能力矩阵、候选原型、决策记录 | 必需能力全部通过任务集 |
| 垂直原型 | 一条端到端最小路径 | 本地成功、失败和终止均可运行 |
| 评估 | 数据集、指标、阈值、基线 | 冻结集达到发布阈值 |
| 可观测性 | 事件 Schema、轨迹、仪表板、告警 | 失败可定位到具体层与步骤 |
| 安全审查 | 威胁模型、控制测试、剩余风险 | 高风险项已修复或被明确接受 |
| 部署 | 版本、灰度、回滚、Runbook | 小流量满足 SLO 且回滚演练通过 |

阶段不是瀑布式单向流程。评估失败可能说明任务定义含糊，安全审查可能要求缩小 Tool 权限，生产轨迹可能暴露新的任务分布。返回上游时应更新 Artifact 和阈值，而不是只调 Prompt。

### 6.1.2 决策记录比技术偏好重要

每个关键选择都应留下四项：当时的需求、比较过的候选、可复现证据、重新评估的触发条件。这样更换模型、Harness 或检索器时，团队可以在同一任务集和边界上比较，而不是重新争论偏好。

## 6.2 先定义 Task 与 Environment

### 6.2.1 Task Contract

“做一个研究助手”不能评估。任务契约应把目标转成可观察行为：

```text
Goal: 从给定的本地资料回答问题，并给出来源位置。
Inputs: 问题、允许的资料目录、截止时间。
Allowed actions: 搜索、读取、生成带引用的草稿。
Forbidden actions: 网络访问、写入资料目录、伪造来源。
Success evidence: 每个事实可追溯到允许资料中的有效片段。
Stop conditions: 证据充分；或 8 个 Tool Step、2 次检索改写、60 秒任一耗尽。
Escalation: 资料冲突或关键证据缺失时请求人工判断。
```

任务集要覆盖真实分布，而不是只有快乐路径。至少包括：常见成功、边界输入、无答案、冲突证据、Tool 错误、权限拒绝、预算耗尽和高影响审批。

### 6.2.2 Environment Contract

Environment 设计决定 Agent 实际能知道和改变什么。对每个 Tool 记录：

| 字段 | 问题 |
| --- | --- |
| 输入 Schema | 哪些参数、类型、范围和额外字段被允许？ |
| 语义规则 | 哪些路径、Query、对象或状态组合有效？ |
| 权限 | 谁能调用，什么参数需要批准？ |
| 副作用 | 读取、写入、外部消息或不可逆影响是什么？ |
| Observation | 成功、空结果、部分结果和失败怎样区分？ |
| 幂等与补偿 | 重放是否安全，失败后如何恢复？ |
| Fixture | 怎样在本地稳定重现行为？ |
| Verifier | 哪个独立信号判断目标满足？ |

先完成这个表，再讨论“Agent 应该有多自主”。自主范围等于允许 Action、权限与预算的交集。

## 6.3 选择 Model 与 Harness

### 6.3.1 用任务集选择 Model

模型选择不是一次排行榜查询。对同一冻结任务集和 Tool Schema，测量：类型化调用正确率、长上下文证据定位、指令遵循、拒绝行为、延迟、总成本和可用性。高能力模型可以用于困难路由或恢复，便宜模型可以处理经过证明的窄任务；路由本身也必须评估。

记录模型版本、参数、上下文构造和 Provider Adapter。模型更新属于依赖升级，应重新跑评估，而不是假设名称相同就行为相同。

### 6.3.2 用能力矩阵选择 Harness

先标记每项能力是**必需**、**有用**还是**无关**，再检查候选方案。

| 能力 | 需求问题 | 原型中应观察的证据 |
| --- | --- | --- |
| Loop 控制 | 是否需要循环、分支、重试和自定义终止？ | 状态与转移可检查，预算强制生效 |
| Tool 边界 | Schema、权限、审批和结构化错误是否足够？ | 无效与越权调用在执行前被拒绝 |
| 状态寿命 | 只需单请求、会话恢复还是长期工作流？ | 检查点可恢复并有版本迁移策略 |
| 人工参与 | 哪些 Action 必须暂停等待决定？ | 审批绑定具体参数，拒绝后状态一致 |
| 并发 | 是否需要并行 Tool 或多执行者协调？ | 依赖、顺序、取消和部分失败可见 |
| 可观测性 | 需要哪些 Trace、指标和评估 Hook？ | 稳定 ID 能关联模型、Tool 与 verifier |
| 部署 | CLI、后台任务、API 服务还是分布式 Worker？ | 隔离、队列、限流、健康检查和回滚可演练 |
| 可移植性 | 是否必须跨模型或数据提供商？ | Adapter 契约测试保留必要语义 |

具体项目名称和当前能力变化快，因此只放在独立的[双语选择矩阵](../../code/go-agentic/06-lifecycle/selection_matrix.md)中。正文使用稳定的选择词汇；矩阵中的名称只是需要再次验证的当前示例。

### 6.3.3 Build、Buy 与最小核心

自建最小 Harness 能提供透明控制和小依赖面，但会承担会话、追踪、审批、并发和部署工作。采用现有组件能缩短交付时间，但必须验证抽象是否保留任务所需的状态、权限和错误语义。选择应以“满足必需能力的最小可维护系统”为目标。

## 6.4 Prototype 与 Evaluation

### 6.4.1 先做垂直切片

第一个原型只需要一条真实端到端路径：一个代表性任务、一组最小 Tool、一个确定性 Environment Fixture、一个 verifier 和一个终止预算。先用固定策略证明 Harness 语义，再接入模型测量决策质量。这样可以把控制缺陷与模型波动分开。

原型必须同时运行至少四类轨迹：

1. 有证据的成功；
2. 可修正失败后的恢复；
3. 无效或越权 Action 的拒绝；
4. 无法完成时的预算终止。

本课程前三个代码目录正好形成这条增长路径：最小循环、循环模式、Tool 与检索 Environment。它们彼此独立，术语和边界一致。

### 6.4.2 评估任务结果、轨迹与系统

| 层级 | 核心问题 | 示例指标 |
| --- | --- | --- |
| 任务结果 | 目标是否由有效证据完成？ | verified success rate、正确性、引用有效率 |
| 轨迹 | 是否用允许且有效的路径完成？ | 无效 Tool 率、重复 Action、恢复率、步数 |
| 安全 | 是否尊重权限与数据边界？ | 越权执行数、敏感数据泄露、审批绕过率 |
| 系统 | 是否在资源目标内稳定运行？ | p50/p95 延迟、每任务成本、超时、可用性 |
| 人因 | 用户能否理解、纠正和信任结果？ | 升级质量、拒绝可理解性、人工处理时间 |

`verified success rate` 的分母应是完整任务集，而不是只统计 Agent 自称完成的样例。成本也应按每个已验证任务统计，而不是只比较单次模型调用。

### 6.4.3 数据集与阈值

开发集用于迭代，冻结回归集用于阻止退化，挑战集用于发现新失败。生产样例进入数据集前应去除敏感信息、确认使用权限并标记来源。每个样例保存输入、环境版本、允许 Action、成功判据和期望停止类型；不要强制一条唯一“黄金轨迹”，除非路径本身属于合规要求。

发布阈值必须在运行冻结集前写明，例如：关键任务 verified success 不低于 95%，越权执行为 0，p95 小于 8 秒，每任务成本不超过给定上限。阈值应按风险分层，不能让大量简单题掩盖少数高影响失败。

## 6.5 Observability 与 Security Review

### 6.5.1 一条可关联的 Trace

每个事件使用稳定的 `run_id`、`step_id` 和 `parent_id` 连接：

```text
task_version, environment_version, model_version,
state, route, tool_name, argument_digest,
permission_decision, observation_code, verifier_result,
latency, token_usage, tool_cost, output_reference
```

Trace 用于回答“在哪一层、哪一步、基于什么证据失败”。日志用于离散事件，指标用于聚合趋势，Trace 用于跨组件因果路径，Artifact 存储大输出。四者不应互相替代。

告警应指向可行动条件，例如 verified success 下降、连续相同错误上升、权限拒绝异常增加、p95 超标或成本漂移。不要为每个模型犹豫或正常空检索报警。

### 6.5.2 安全审查从权限图开始

威胁模型应画出用户、模型、Harness、Tool、数据源、外部系统和人工审批之间的信任边界。

| 威胁 | 入口 | 主要控制 | 验证方法 |
| --- | --- | --- | --- |
| Prompt / 检索注入 | 用户输入、网页、文档、Tool 输出 | 指令与数据隔离、来源、最小权限 | 对抗 Fixture 尝试扩大权限 |
| 过度授权 | 宽泛 Tool、共享凭证 | 细粒度能力、短期凭证、参数绑定审批 | 越权调用必须在执行前失败 |
| 数据泄露 | Prompt、Trace、错误、外部调用 | 数据分类、掩码、出站策略、保留期限 | Canary 数据与日志审计 |
| 不安全副作用 | 文件写入、消息、交易、部署 | 沙箱、幂等、审批、补偿操作 | 重放、部分失败和回滚测试 |
| 供应链变化 | 模型、依赖、Tool、索引升级 | 版本锁定、来源验证、回归集 | 升级前后差分评估 |
| 资源耗尽 | 无限 Loop、大输出、并行风暴 | 步数/时间/成本预算、并发限制 | 压力与预算终止测试 |

安全评审输出不是一句“已安全”，而是威胁、控制、测试证据、负责人和剩余风险清单。

## 6.6 Deployment 与持续运行

### 6.6.1 发布门槛

上线前检查：

- 版本化 Prompt、Tool Schema、模型配置、Environment 与评估集；
- 生产权限小于或等于评估时测试的权限；
- 超时、重试、幂等、取消、检查点和故障恢复已演练；
- 仪表板与告警能看到成功、安全、延迟和成本；
- Runbook 标明降级、禁用 Tool、暂停流量和回滚负责人；
- 数据保留、删除、审计和用户告知满足组织要求。

### 6.6.2 灰度、回滚与状态迁移

先以影子流量或少量低风险任务运行，再逐步扩大。灰度比较必须使用任务结果，而不是只看进程健康。回滚单元应包含相互兼容的 Prompt、模型配置、Tool Schema 和状态版本。

有持久会话时，旧状态可能无法被旧代码读取，因此需要向前兼容、迁移脚本或停止接收新任务后排空。外部副作用不能靠代码回滚自动撤销；必须使用幂等键、事务或显式补偿。

### 6.6.3 持续评估

生产只记录经过治理的最小数据。定期从失败、人工升级、低置信度和新任务类型中抽样，经脱敏与标注后加入挑战集。发现退化时先定位是任务分布、模型、Harness、Tool、数据还是部署变化，再更新对应控制和回归样例。

## 6.7 生命周期反模式

| 反模式 | 后果 | 替代做法 |
| --- | --- | --- |
| 先选技术再定义任务 | 用候选能力改写需求 | 先冻结任务契约和必需能力 |
| Demo 即评估 | 快乐路径掩盖拒绝与终止缺陷 | 建立分层任务集与阈值 |
| 只评最终文本 | 越权或浪费路径不可见 | 同时评分结果、轨迹、安全与系统 |
| 只调 Prompt | 控制、工具或数据缺陷被掩盖 | 先定位责任层，再修改最小部件 |
| 全量发布 | 小概率高影响故障直接触达用户 | 灰度、Kill switch 和回滚演练 |
| 记录一切 | 泄露敏感数据且增加成本 | 按用途最小化、掩码和设保留期 |
| 无版本状态 | 升级后无法恢复或比较 | 版本化所有输入与持久状态 |

## 6.8 本章小结

- Agent 开发从任务与 Environment 开始，以可评估边界约束自主性。
- Model 与 Harness 选择必须由冻结任务集和能力矩阵支持。
- 垂直原型先证明成功、恢复、拒绝和终止，再扩大功能。
- 评估同时覆盖结果、轨迹、安全、系统与人因，发布阈值按风险分层。
- 可观测 Trace 连接模型、Tool、权限、Observation 与 verifier；安全审查验证信任边界。
- 部署需要版本、灰度、回滚、状态迁移与持续评估，而不是一次上线结束。

## 习题

1. 为“根据本地工单草拟回复”写 Task Contract，包含允许 Action、禁止 Action、成功证据、预算和升级条件。
2. 为该任务填写 6.2.2 的 Environment 表，并设计一个确定性权限拒绝 Fixture。
3. 使用选择矩阵把八项能力标为必需、有用或无关；写出两个候选原型必须提供的证据，不按名称直接选择。
4. 设计包含 12 个样例的评估集，覆盖成功、边界、无答案、冲突、Tool 错误、权限和预算；为高风险子集设置独立阈值。
5. 写一条失败 Trace，并说明仪表板、告警和 Runbook 分别如何帮助处理它。
6. 为带外部写入副作用的 Agent 设计 5% 灰度、Kill switch、幂等键和补偿流程。

## 掌握标准

当你能从一个模糊产品目标产出 Task 与 Environment 契约；能用任务集和能力矩阵选择 Model 与 Harness；能定义结果、轨迹、安全和系统阈值；能从 Trace 定位失败；并能给出经过安全审查、可灰度、可回滚、可持续评估的发布方案时，即达到本章要求。

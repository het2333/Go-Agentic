毕业设计不是再做一个更长的 Demo，而是证明你能将一个含糊需求变成可运行、可评测、可审计、可恢复和可发布的 Agentic AI 系统。

## 25.1 选题与任务契约

好选题有可观测的 Environment、多步决策、外部工具、可验证结果和明确风险边界。如果任务一次 Prompt 就能稳定完成，Workflow 或普通程序可能更合适。

任务契约必须冻结：

- 目标用户和触发条件；
- 输入、输出和不处理的情况；
- 可读、可写资源与权限；
- 成功、失败、停止和升级条件；
- 延迟、Token、Tool Call 和金额预算；
- 高风险行动的审批与回滚方式。

## 25.2 基线与架构

至少实现一个非 Agent 基线（规则、单次 LLM 或固定 Workflow）。多 Agent 项目还必须实现单 Agent 基线。没有基线，就无法证明自主循环、Memory 或多 Agent 真的带来了收益。

架构文档应只保留能改变质量、安全、延迟或运营方式的边界：

```text
User / Trigger
      ↓
Task Contract → Runtime / Queue → Agent Loop
                                     ↓
                         Tool / Environment / Memory
                                     ↓
                              Verifier / Approval
                                     ↓
                           Artifact / Audit / Metrics
```

## 25.3 里程碑与变更管理

1. **M0 任务冻结：** 需求、边界、基线和评测集版本化。
2. **M1 最小闭环：** 一条任务可以 Observe–Act–Verify–Stop。
3. **M2 失败可见：** 工具错误、超时、验证失败和预算耗尽可复现。
4. **M3 安全闭环：** 权限、审批、幂等和审计通过故障测试。
5. **M4 评测冻结：** 基线、主方案、消融和误差分析可重跑。
6. **M5 发布候选：** UI、Runtime、可观测性、运行手册和回滚齐备。

里程碑之间可以修改系统，但修改评测集、成功阈值或安全规则时要新建版本，不要覆盖原始契约。

## 25.4 评测、消融与误差分析

评测至少覆盖：

- 任务完成率与部分完成；
- 证据/引用正确性；
- Tool Call 成功率、冗余调用与无效循环；
- 延迟、Token、Tool 和计算成本；
- 审批准确性与未授权副作用；
- 中断、恢复与重放一致性。

消融每次只移除一个关键机制，例如 Reranker、Long-term Memory、Verifier、Compaction 或第二个 Agent。按失败的第一原因归类，不要只用“幻觉”统称所有问题。

## 25.5 安全评审

安全文档需回答：

1. 威胁主体、资产和信任边界；
2. Prompt Injection、越权 Tool Call、数据外泄和供应链风险；
3. 最小权限、沙箱、参数验证和输出验证；
4. 审批范围、过期、拒绝和撤销；
5. Secrets、PII、Trace 和 Memory 的保留/删除策略；
6. 发生事故时如何停止、回滚、通知和保全证据。

红队测试必须真正走过 Tool/Runtime 边界，而不是只问模型“你会不会泄密”。

## 25.6 Reproducibility Pack

标准交付树为：

```text
capstone/
├── README.md
├── task_contract.md
├── architecture.md
├── eval/
│   ├── dataset.jsonl
│   └── report.md
├── traces/
├── security_review.md
└── reproduction.md
```

`reproduction.md` 中包含安装、Fixture 版本、模型配置、离线测试、可选真实服务测试、预期指标范围和已知限制。不提交 API Key、用户数据或未脱敏 Trace。

## 25.7 五分钟 Demo 与发布

Demo 只需证明五件事：

1. 任务为什么需要 Agent；
2. 一条成功轨迹和关键证据；
3. 一个真实失败如何被发现与处理；
4. 一次审批、拒绝或取消；
5. 与基线相比的质量、成本和风险结论。

发布前检查版本固定、数据迁移、密钥轮换、告警、运行手册、回滚、数据删除和成本上限。

## 25.8 两套验收 Rubric

### 25.8.1 Agent 应用工程路线

| 维度 | 分值 |
| --- | ---: |
| 任务价值与完成度 | 20 |
| Loop、Tool、Context 与 Runtime 设计 | 20 |
| 证据、评测、基线与消融 | 20 |
| 安全、审批、审计与隐私 | 20 |
| UI、失败恢复与运营性 | 10 |
| 可复现包与表达 | 10 |

### 25.8.2 全栈 Agentic AI 路线

| 维度 | 分值 |
| --- | ---: |
| Agent 系统价值与完成度 | 15 |
| 模型/训练/推理问题定义 | 15 |
| 数学、容量和拓扑证据 | 15 |
| 实验、基线、消融与误差分析 | 20 |
| 安全、审批、审计与隐私 | 15 |
| Runtime、容错、可观测性与 SLO | 10 |
| 可复现包与表达 | 10 |

两条路线都要求总分不低于 75，且证据、安全、失败恢复和可复现性不得缺失。

## 25.9 Portfolio 与 Reviewer Pack

对外展示时包含一页摘要、架构图、一分钟和五分钟 Demo、评测表、一个失败案例、安全边界与复现入口。用“任务—基线—变更—证据—剩余风险”表达工作，不要只列技术名词。

## 25.10 未来方向

完成课程后，可以沿以下方向继续：

- 可验证 Reward 与环境生成；
- 长期 Memory 的冲突、遗忘与个性化治理；
- Computer Use 的感知、可恢复动作与安全边界；
- 跨 Agent 身份、能力发现和协议版本治理；
- 模型—Harness—Environment 联合评估；
- 计算、延迟、能耗与任务价值之间的系统优化。

最后的掌握标准不是背出架构名词，而是能够回答：这个系统为什么需要 Agent，证据在哪里，失败时会怎样，谁能阻止它，以及另一个人如何复现你的结论。

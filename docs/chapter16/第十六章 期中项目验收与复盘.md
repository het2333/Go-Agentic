第 13–15 章已经把 Loop、Tool、Context、Memory、Protocol、Evaluation 和 Safety 放入了真实项目。本章不再增加新概念，而是停下来回答一个更严格的问题：

> 这个 Agent 是“演示过一次”，还是已经可以被别人复现、评测和审查？

## 16.1 期中交付物

从以下三条路线中选一条：

1. 真实任务执行 Agent；
2. Deep Research Agent；
3. 有界多智能体系统。

最小交付包必须包含：

```text
midterm/
├── README.md              # 一句话任务、安装、运行和限制
├── task_contract.md       # 输入、输出、权限、停止条件
├── architecture.md        # Loop、Tool、State、Environment 边界
├── eval/
│   ├── cases.jsonl        # 至少 10 个固定测试任务
│   └── report.md          # 基线、指标、失败分类
├── traces/                # 成功与失败轨迹
├── security_review.md      # 副作用、审批和敏感数据
└── reproduction.md         # 从空环境复现结果
```

“我的电脑上能跑”不是验收标准。复现文档要说明版本、模型、环境变量、Fixture、随机性和期望输出。

## 16.2 系统设计画布

用一页回答七个问题：

| 区域 | 必须回答 |
| --- | --- |
| Task | 谁在什么情况下交给 Agent 什么任务？ |
| Success | 哪些可观察条件同时成立才算成功？ |
| Environment | Agent 可以读取和改变什么？ |
| Loop | 如何观察、选择行动、验证和停止？ |
| State | 哪些状态进入 Context，哪些持久化？ |
| Safety | 哪些行动必须审批，如何回滚？ |
| Evidence | 用什么证明输出来自真实执行而非自述？ |

画布中每个箭头都要对应一个可观测事件：Tool Call、Environment Result、Validation Result、Approval Decision 或 Final Artifact。

## 16.3 证据、安全与可复现性

一条可用轨迹至少包含：

```json
{
  "task_id": "case-007",
  "input_version": "fixture-v2",
  "model": "provider/model-version",
  "actions": [],
  "approvals": [],
  "evidence": [],
  "validators": [],
  "final_state": "succeeded",
  "cost": {"tokens": 0, "seconds": 0.0}
}
```

审批不是页面上的一个“确认”按钮，而是一个有语义的状态：审批什么动作、目标是谁、预计副作用是什么、支持决定的证据是什么、由哪位审批人（decision maker）作出决定，以及该决定何时过期。

## 16.4 百分制验收 Rubric

| 维度 | 分值 | 满分标准 |
| --- | ---: | --- |
| 任务完成 | 25 | 在固定任务集上达到预先声明的成功阈值 |
| 证据与来源 | 15 | 所有关键结论可追溯到 Tool/Environment 结果 |
| 评测与基线 | 15 | 有固定数据、单 Agent/规则基线、指标与误差分析 |
| 安全与审批 | 20 | 副作用最小权限，高风险操作可预览、审批、拒绝和审计 |
| 失败恢复 | 15 | 超时、工具错误、验证失败和预算耗尽均有明确终止或恢复路径 |
| 可复现性 | 10 | 新环境可按文档运行 Fixture、评测和代表性轨迹 |

通过条件：总分不低于 70，且“安全与审批”不得为 0。如果项目完全没有副作用，也必须在任务契约中说明这一点，而不是留空。

## 16.5 失败复盘

选择一条“最接近成功但最终失败”的轨迹，按以下顺序复盘：

1. 用外部可观测语言描述失败；
2. 找到第一个错误决策，不只看最后一个异常；
3. 判断它属于 Model、Context、Tool、Loop、Environment 还是 Runtime；
4. 只改动一个原因；
5. 在同一固定任务集上重跑；
6. 报告改进、回归和剩余风险。

## 16.6 前半程速查

| 症状 | 先检查 | 不要先做 |
| --- | --- | --- |
| 回答无证据 | Tool/Environment 结果是否进入 Context | 立即换更大模型 |
| 工具反复调用 | 终止条件、去重键和失败分类 | 无限增加最大轮数 |
| 长任务遗忘约束 | 结构化状态、Compaction 和 JIT Context | 把全部历史永久塞入 Prompt |
| 评测结果波动 | 固定 Fixture、模型版本、评分器和重试策略 | 只展示最好的一次 |
| 出现意外副作用 | 权限边界、Dry Run、审批门和幂等性 | 依赖 System Prompt 里的一句警告 |

## 16.7 两条后续路线

**Agent 应用工程路线：** 如果你的目标是产品、企业应用或 Agent 平台，可以直接进入第 23–25 章。

**全栈 Agentic AI 路线：** 如果你需要理解模型为什么这样运作、如何训练以及如何高效服务，按顺序继续第 17–25 章。

这是两条学习路线，不是两种质量等级。应用路线不要求大模型训练，但同样要求证据、评测、安全和可复现性。

## 16.8 练习与通过标准

1. 冻结 10 个测试任务，在修改 Agent 前写下成功阈值。
2. 记录一条成功轨迹、一条工具失败轨迹和一条审批被拒绝的轨迹。
3. 用百分制 Rubric 自评，再请另一个人独立评分，说明分歧来源。
4. 在新目录或容器中按 `reproduction.md` 重跑项目。

当且仅当以上四项完成、总分达到 70 且安全不为零时，才进入后半程。

前两章分别建立了企业执行契约与深度研究契约。本章把两者组合成一个刻意受限的多智能体项目：Planner 定义任务，Researcher 整理证据，Reviewer 拒绝不合格产物，Executor 只在人工批准后执行。旧文件名与 Docsify URL 继续保留，但课程项目已不再是赛博小镇。

本章默认代码只使用 Python 标准库，数据固定在内存中，不访问网络、不调用模型，也不需要 API Key。Pi 兼容的观察—行动—验证 Loop 仍是唯一连续实践主线；Hermes 只用于说明长期运行时会增加哪些服务。

## 15.1 先证明需要多智能体

### 15.1.1 问题、边界与成功条件

案例仍是供应商交付异常。邮件声称已发货，物流记录却可能仍为 `pending`。系统可以准备澄清邮件，但不能修改采购订单或合同。成功不是“角色都说过话”，而是：证据覆盖完整、矛盾未被隐藏、审查结论绑定具体产物、执行动作绑定人工批准、重放不产生第二次业务效果。

多智能体并非默认答案。它引入更多步骤、上下文、故障点和成本，只有当角色分离显著提高质量或降低风险时才值得采用。

### 15.1.2 单智能体基线

先运行可比较的单智能体基线。它读取同一 Fixture、面对同一任务，并使用同一评分标准。两种架构都经过草稿、动作预览、人工批准、Gateway 执行与审计安全外壳；基线只把内部推理压缩为一个角色。它用 2 个单位完成推理，再分别用 1 个单位生成预览和执行，总成本为 4。在简单案例中足够，在冲突案例中会把“已发货”误当成确定事实。

| 案例 | 基线质量 | 安全违规 | 基线成本 | 多智能体质量 | 多智能体成本 | 是否值得额外成本 |
|---|---:|---:|---:|---:|---:|---|
| `routine` | 100 | 0 | 4 | 100 | 6 | 否：质量没有提高 |
| `conflicting_evidence` | 55 | 1 | 4 | 100 | 9 | 是：+45 分且消除 1 次违规 |

教学判据是：多智能体流程必须完成、质量至少提高 20 分，并且安全违规少于基线。该阈值属于本 Fixture；真实项目应在部署前基于代表性任务、错误代价和预算冻结自己的阈值。

## 15.2 四个角色与可验证契约

### 15.2.1 职责矩阵

| 角色 | 输入 | 产物 | 明确禁止 |
|---|---|---|---|
| Planner | 任务目标、风险与预算 | `plan` | 编造证据、执行外部动作 |
| Researcher | `plan` 与来源记录 | `research_findings` | 覆盖矛盾、批准自身结论 |
| Reviewer | 特定版本的 Findings | `review` | 静默改写被审产物、执行动作 |
| Executor | 已接受的 Review 与 Findings | `action_preview`、回执 | 无批准执行、扩大动作范围 |

角色名不构成安全边界。真正的边界来自 Harness：输入类型、允许的接收者、成本上限、Artifact Digest、状态机与 Gateway 授权检查。Prompt 中写“你是 Reviewer”不能替代这些约束。

### 15.2.2 消息与不可变产物

每个跨角色交接都是显式 `Message`，包含发送者、接收者、消息类型、Artifact ID 和下一步指令。接收者读取固定版本，而不是依赖一段可能被压缩的聊天历史。

```python
@dataclass(frozen=True)
class Artifact:
    artifact_id: str
    version: int
    kind: str
    author: str
    content: tuple[tuple[str, str], ...]
    parent_ids: tuple[str, ...]
    digest: str
```

修订会生成 v2，并把 v1 的 ID 写入 `parent_ids`。v1 保留不变；Audit Log 因此能回答“Reviewer 当时拒绝了什么”和“后来改了什么”。Digest 覆盖 ID、版本、作者、内容和父链接，后续批准再绑定动作预览的 Digest。

## 15.3 有界编排状态机

### 15.3.1 正常数据流


执行分为 `prepare()` 与 `execute(approval)`。前者最多生成动作预览；后者验证批准后才接触 Gateway。这一暂停点使 UI、CLI 或工单系统能够展示完整目标、动作、范围与哈希。

### 15.3.2 Reviewer 拒绝与有界重试

冲突案例的 v1 Findings 同时记录 `email=shipped` 与 `logistics=pending`，却建议把发货标为已确认。Reviewer 返回 `rejected` 和问题“矛盾证据未解决”。默认 `max_review_retries=1`，Researcher 因而只能产生一个 v2；v2 将建议收窄为“请求澄清且不修改订单”。

如果第二次仍被拒绝，状态进入 `review_rejected`，不产生动作预览。预算的语义是“最多允许多少次额外修订”，不是无限自我反思。Reviewer 的否决必须改变控制流，不能只留一段建议后继续执行。

### 15.3.3 失败隔离、预算与批准

| 触发条件 | 终态或暂停态 | 下游效果 | 审计证据 |
|---|---|---|---|
| 角色抛出错误 | `failed` | 后续角色不运行 | `role_failed` |
| 下一角色会超成本 | `budget_exhausted` | 不运行该角色 | `budget_exhausted` |
| Reviewer 重试耗尽 | `review_rejected` | 无 Preview、无执行 | `workflow_stopped` |
| 无批准、过期或哈希不符 | `awaiting_approval` | 无执行 | 拒绝原因与 `last_error` |
| 人工拒绝 | `approval_rejected` | 终止且无执行 | `approval_rejected` |
| 批准后执行预算不足 | `budget_exhausted` | 不接触 Gateway | `approval_recorded` 后跟 `budget_exhausted` |
| Gateway 或幂等键冲突 | `gateway_failed` | 不重复执行 | 失败类型、动作哈希与恢复提示 |
| 批准匹配 | `completed` | 幂等执行一次 | 批准、回执与完成事件 |

批准只对一个 `action_hash` 和有效时间窗有效。时间必须带时区，且批准未过期。若目标、动作、范围或来源 Digest 变化，就必须生成新 Preview 并重新批准。Gateway 把幂等键绑定 Preview Digest；重复执行返回同一回执，而同键不同载荷会失败。

## 15.4 运行离线项目

### 15.4.1 默认路径

在仓库根目录执行：

```bash
python3 code/go-agentic/15-multi-agent-system/workflow.py
python3 -m pytest code/go-agentic/15-multi-agent-system/test_workflow.py -q
```

输出固定为：

```text
routine: baseline_quality=100 multi_quality=100 baseline_cost=4 multi_cost=6 worth_extra_cost=False
conflicting_evidence: baseline_quality=55 multi_quality=100 baseline_cost=4 multi_cost=9 worth_extra_cost=True
```

该路径不会安装依赖或读取环境变量。`.invalid` 收件地址只是虚构标识；内存 Gateway 不会发送真实邮件。

### 15.4.2 阅读测试覆盖的行为

测试直接运行真实 Workflow，而不是断言 Mock 被调用。它覆盖：冲突修订产生 v1/v2、Frozen Artifact 无法原地修改、六次交接顺序、一次 Review 重试、无批准与错哈希不执行、正确批准重放只有一个效果、Reviewer 拒绝耗尽、角色错误、成本耗尽、人工拒绝、批准后执行预算耗尽、真实幂等键冲突，以及两种架构使用相同安全外壳的共享指标。

```python
system = build_demo_workflow(case_id="conflicting_evidence")
prepared = system.workflow.prepare()
approval = ApprovalDecision(
    approval_id="approval-001",
    actor="operator",
    approved=True,
    action_hash=prepared.preview.digest,
)
completed = system.workflow.execute(approval)
assert completed.status == "completed"
assert len(system.gateway.effects) == 1
```

## 15.5 共同评估，而不是比较角色数量

### 15.5.1 指标定义

| 指标 | 定义 | 目的 |
|---|---|---|
| `quality_score` | 0–100 的任务结果评分 | 比较最终正确性与证据处理 |
| `safety_violations` | 越权、隐藏冲突或未批准执行次数 | 防止高分掩盖危险轨迹 |
| `steps` | 角色调用与外部执行总数 | 衡量轨迹长度 |
| `cost_units` | 冻结的角色成本之和 | 形成可复现预算 |
| `handoffs` | 显式 Message 数 | 衡量协调负担 |
| `retries` | Reviewer 拒绝后的额外修订数 | 检查上限是否生效 |
| `reviewer_rejections` | Reviewer 实际否决数 | 区分审查存在与审查有效 |

同一案例必须用同一输入、评分器、禁止行为集合，以及相同的草稿、预览、批准、执行与审计外壳。固定外壳成本后，只比较推理与角色协调带来的差异。不能给多智能体更完整的证据，再宣称架构更好；也不能只比较“是否完成”，忽略它是否通过错误动作完成。

### 15.5.2 何时升级架构

简单、低风险、单领域、可快速验证的任务优先使用单智能体。出现以下两项以上时，才值得试验多智能体：证据来自多个权限域；需要独立反证；产物必须经过职责分离；一次错误的代价高；任务可被清晰拆成可验收 Artifact；历史评估显示单智能体在某一边界持续失败。

即使多智能体胜出，也应通过消融验证每个角色：移除 Reviewer 是否让冲突错误重新出现？合并 Planner 与 Researcher 是否保持质量并降低成本？如果答案表明某角色没有增益，就删除它。

## 15.6 Pi 主线与长期运行时对照

### 15.6.1 Pi 兼容实践主线

Pi 的小 Harness 让本章核心保持可见：读取任务和 Artifact 是 Observation；角色策略选择下一步；文件、命令或自定义 Tool 是 Action；测试与 Reviewer 是 Verification；会话树和文件可承载交接。实际接入 Pi 时，应把角色协议和审查规则放进可版本化的 Skill/Extension/文件契约，而不是让四个无限自由的聊天进程互相提示。

本地 Python Fixture 是这些概念的可执行缩影，不是 Pi SDK 的复刻。它故意省略模型，以便先验证控制结构。

### 15.6.2 Hermes 作为长期运行时对照

根据截至 **2026-09-13** 的官方资料，Hermes Agent 将持久记忆、Cron 定时任务、消息 Gateway、MCP 集成与隔离 Subagent 放在一个长期运行时中。这些能力改变的是部署问题：任务如何跨 Session 记住状态，何时被唤醒，从哪个渠道收件，怎样调用外部系统，以及子任务如何隔离。

| 长期需求 | 本章 Pi 兼容 Fixture | Hermes 对照提出的问题 |
|---|---|---|
| Memory | Artifact 与 Audit 在单进程内 | 记忆写入、检索、过期与租户隔离 |
| Cron | 无后台唤醒 | 重入、错过调度、时区与重复触发 |
| Gateways | 内存效果 | 渠道认证、速率限制与回执关联 |
| MCP | 仅概念边界 | Server 权限、来源信任与 Tool 版本 |
| Subagents | 顺序角色对象 | 沙箱、资源配额、取消与结果回收 |

Hermes 不成为本课程的可执行主线。将本例迁移到长期运行时之前，必须先把状态、Artifact、审批与幂等语义放进持久存储。DeepSeek Harness 仍只代表插件化 Harness 的架构对照，本章不扩展第二条实现路线。

## 15.7 从 Fixture 到生产

### 15.7.1 安全与运维契约

生产系统至少需要：按角色和租户授权；Artifact 与 Audit 的耐久存储和完整性校验；敏感字段最小化与保留期限；不可信输入隔离；Tool 参数 Schema；并发幂等与 Provider 回执查询；审批身份、有效期和撤销；超时、取消和补偿；指标、追踪、告警与事件响应。

多智能体会放大 Prompt Injection 与权限串联风险。Researcher 读到的网页不能指挥 Executor；Reviewer 的“通过”不能扩大 Gateway 权限；共享 Memory 不能成为跨租户数据通道。每个角色只获得完成其契约所需的最小能力。

### 15.7.2 局限

Fixture 的 100 分不是现实准确率。评分与案例都是手工固定的，只能证明控制流、版本、边界和指标计算可重复。它不证明模型能理解真实合同、不证明证据语义蕴含、不模拟并发写入，也不提供分布式 exactly-once。生产结论需要私有评估集、盲评、失败分类、压力测试和持续监控。

## 15.8 练习、掌握标准与资料

### 15.8.1 练习

1. 新增 `missing_evidence` 案例：Researcher 必须停止，补证后在同一任务中生成新版本。
2. 给 Approval 增加撤销记录，用测试证明尚未过期但已撤销的批准无法执行。
3. 将 `max_review_retries` 设为 0、1、2，绘制质量、成本和延迟曲线。
4. 做一次消融：移除 Planner 或 Reviewer，使用同一评分器说明变化。
5. 设计一个 Hermes 部署草图，明确 Memory、Cron、Gateway、MCP 和 Subagent 的持久化与权限边界，但继续用本地 Fixture 验证语义。

### 15.8.2 掌握标准

当你能先建立单智能体基线，用显式消息和不可变 Artifact 解释每次交接，让 Reviewer 的拒绝真实改变控制流，在预算或角色失败时阻止下游执行，把人工批准绑定动作哈希，并用共享指标证明何时值得支付协调成本时，就掌握了本章。
